# Heimdall dashboard

The web app that shows the fleet. It is a TanStack Start app (React, Tailwind CSS v4, shadcn/ui) that reads the Hub's PostgreSQL database directly through server functions and never writes to it. See [ADR-0015](../../docs/decisions/0015-dashboard-is-its-own-app-reading-the-hubs-database.md).

It runs under Bun, like the Hub, and uses Bun's built-in `SQL`.

## Database URL

The app reads the URL of the Hub's database from the first of these that is set:

1. The `HEIMDALL_DATABASE_URL` environment variable.
2. `[database] url` in the Hub's config file, `~/.config/heimdall/hub.toml`.

The app opens the connection on the first request, so it starts and builds without a database.

## Run

Run these from the repository root, after `bun install`.

| Task                                                | Command                                  |
| --------------------------------------------------- | ---------------------------------------- |
| Develop, on <http://localhost:3000>                 | `bun run --cwd packages/dashboard dev`   |
| Build the app into `.output/`                       | `bun run --cwd packages/dashboard build` |
| Serve the built app from source                     | `bun run --cwd packages/dashboard start` |
| Build the app and compile `dist/heimdall-dashboard` | `bun run build:dashboard`                |

`dev` and `build` run Vite under the Bun runtime (`bun --bun vite`), and the build uses Nitro's `standard` preset with the static assets inlined, so `.output/` holds a server that needs no files beside it. `bun run build:dashboard` builds the app and compiles it into `dist/heimdall-dashboard`, a single self-contained binary. `start` runs `bun src/main.ts serve`, which serves the built `.output/` from source, so run `build` first. The dev server takes `--port`.

## Settings

`heimdall-dashboard serve` serves the pages, the server functions, `GET /api/health`, and the records read, `GET /api/v1/records` ([Reading the records back](../../docs/spec.md#reading-the-records-back)). Both API routes answer any method but GET and HEAD with 405. Each setting comes from its flag, then its environment variable, then the configuration file: the one `--config` names, or else the first of `.config/heimdall/dashboard.toml` and `.config/heimdall/dashboard.json` found in the working directory and each directory above it below home (up to the filesystem root when the working directory is outside home), then in the home directory (`~/.config/heimdall/dashboard.toml`), then `config.toml` or `config.json` in `$XDG_CONFIG_HOME/heimdall-dashboard` (`~/.config/heimdall-dashboard` by default). `--no-config` reads no file, and a file that cannot be parsed is skipped with a warning. The database URL comes from `HEIMDALL_DATABASE_URL` or else the home `~/.config/heimdall/hub.toml` alone:

| Flag     | Variable                  | File key | Default     |
| -------- | ------------------------- | -------- | ----------- |
| `--host` | `HEIMDALL_DASHBOARD_HOST` | `host`   | `127.0.0.1` |
| `--port` | `HEIMDALL_DASHBOARD_PORT` | `port`   | `3000`      |

A port of 0 picks a free one. The file holds no secret, and the database URL is not one of its settings: it comes from the section above.

The dashboard's HTTP idle timeout is 60 seconds, allowing slow page queries to finish before the connection closes.
The database statement timeout remains 30 seconds. The Hub retains its 10-second HTTP idle timeout.

`GET /api/health` answers 200 with `{"database":"ok","version":"<version>"}` when the Hub's database answers within 2 seconds, and 503 with `{"database":"not answering","version":"<version>"}` when it does not or no URL is configured.

## Run as a Service

`heimdall-dashboard service install | uninstall | start | stop | restart | status` work as the Hub's do, through the `@heimdall/service` package: a systemd user unit on Linux and a launchd user agent on macOS, named `com.dbtlr.heimdall.dashboard`. The unit runs `serve -v` from home, so its log names each config value the dashboard ignores, and appends to `~/.local/state/heimdall/dashboard.log`, which the binary rotates itself. `service install --port N` stores `port = N` in `dashboard.toml` only when it changes. `status` always exits 0 and shows the unit's state, a `health` line asked of `http://127.0.0.1:<port>/api/health` (with `restart pending` when the running version differs from the binary), and the unit, log, and config paths. Only a compiled binary may `install` or `uninstall`. The README at the repository root covers the commands, and [Running Heimdall with Fleet](../../docs/fleet.md) the declarations that install the dashboard.

## Pages

A top bar spans every page. It holds the name, the fleet verdict, "All clear" when no paired item is at alert or warning level and else the count of each open level, and, from 640 px up, the sections and the jump box. The sections are, in order, Home (`/`), Systems (`/systems`), Services (`/services`), Agents (`/agents`), Maintenance (`/maintenance`), and Activity (`/timeline`). The section a page belongs to is marked: Compare belongs to Home, the Maintenance page to Maintenance, a System or Condition page to Systems, a Service page to Services, and a Session page to Agents. Below 1024 px the sections take a row of their own. The verdict waits, as on Home, for a paired System to report, and is left out when its read fails. All pages share one content frame; from 1024 px up it fills the window's width inside 14 px gutters. A page row under the top bar holds the range picker of Compare; the Agents range picker sits on its page's title row.

A maintenance note is an open Pending update or Reboot required Condition at the note level on a paired System. The Hub still raises it and the Timeline and its Condition page still show it, but the dashboard keeps it out of the open Conditions: it counts in neither the top bar's nor the phone header's note count, nor the verdict's notes that can wait, nor a tile, nor a System's Open Conditions, nor Compare's Open now. Home's Maintenance card and a System's Maintenance section list it instead. At warning or alert, either kind is no maintenance note and shows wherever other Conditions do. Paired Systems' Service restarted notes likewise live on Services, but stay in Compare's Open now and on tiles.

The jump box finds a System, a Service (shown with its System), a project, or a Session by the start of its id. A bare `/` focuses it unless an input or other editable field has focus, and a click does too; below 640 px, where the top bar hides it, `/` is left to the browser. Typing lists up to 10 matches, Systems first, then Services, projects, and Sessions, and within each kind the names that start with the text before those that contain it; an empty box lists nothing, and a text that matches nothing says so. The arrow keys move through the list, Enter opens the active match, and Escape clears and closes the box. On the More page the list stops above the bottom bar and scrolls inside itself, keeping the active match in view. A System opens its page, a Service its Service page, a project the Agents page over 30 days broken down by project and picked to it, and a Session its Session page. Its names come from one read each time it gains focus: every System, paired or with history kept; every paired System's Services; the Sessions whose transcript ran in the last 30 days; and the projects of the Sessions with a request in those 30 days, so the Agents page a project opens always has it to pick.

On phones, a raised tab bar at the bottom links to Home, Services, Agents, Activity, and More. Each tab fills a fifth of the bar's width, shows an icon over its label, and turns the primary color when the page belongs to it: Systems, System, Condition, and Maintenance pages belong to More. The legend lists five keys before the rest fold into "N more", and from 640 px up ends with a hint that picking a key filters the table. A key with unpriced requests reads "At least", and one with none priced reads "No list price", with a note that unpriced requests may change the shares and order. Tapping a key sets `pick` in the URL, dims the other keys' segments in every bar (the "others" segment stays lit when the pick is one of them), and filters the Sessions list to that project, System, Harness, or, for the model breakdown, the Sessions that used that model; their amounts still cover the whole period, so under a model a Session's amount includes what its other models cost. Tapping the key again, or the chip above the list, clears the pick; changing `by` or the range clears it too. Sessions with no working directory and requests with an empty model have the empty `pick`.

The model breakdown reads the Hub's stored per-Session model totals for Sessions whose request spans fit inside the period, and prices requests for those crossing a boundary, as for Session totals. Stored model totals are refreshed with the Session totals, so they have the same refresh lag.

The Agents view reads stored totals for Sessions whose request spans fit inside the period. Sessions crossing either boundary read and price only requests inside it. The chart works the same way per bar: a Session whose requests in the period all fall in one bar takes its stored model totals, and only a Session crossing a bar's edge or the period's is priced, request by request and only for that bar, so its cost follows the period's Sessions, not the archive. Its stored spans and totals have the same refresh lag as other pages. After a price change, boundary amounts can reflect the new prices while stored totals still use the old prices. A refresh brings them into agreement; a backlog can take several refreshes. The fleet total always sums the displayed amounts. The page waits for the browser's time zone before displaying totals, and the range and zone travel in its URL, together with the breakdown and its pick and the table's `sort`, `dir`, and `page`, each left out at its default.

The Hub sets every Condition's level: note, warning, or alert ([ADR-0017](../../docs/decisions/0017-the-hub-sets-condition-levels.md)). The dashboard reads stored levels and transitions from one consistent database snapshot. Disk limits and per-System overrides belong in the Hub configuration.

Every page but the Session page reads its data again every 15 seconds while its tab is visible, through the router's invalidation, and at once when the tab becomes visible again. A tick that finds the previous load still running is skipped.

The Agents query benchmark runs against a disposable test database with 800 Sessions and 200,000 requests:

```sh
bun packages/dashboard/scripts/benchmark-agents.ts
```

It checks request counts against the fixture facts and reports the first read, warm median, and worst duration for each period. It uses the test PostgreSQL harness and never reads `HEIMDALL_DATABASE_URL`.

## Mobile status area

Mobile headers use an opaque raised surface and leave the top safe area clear.
The viewport uses `viewport-fit=cover`; page content also respects the left and right safe areas.
A real fixed element paints the top edge, including at least 6 pixels on narrow screens and devices with a coarse pointer.
Wide screens with a fine pointer paint only the reported top inset, leaving desktop scrolling content clear.
This gives Safari a persistent background to sample for its status area while the page scrolls.
Keep that element opaque and free of filters; a pseudo-element or a `theme-color` tag alone does not provide the same sampling target.

Check native status-area behavior in an installed iOS web app after layout changes.
Desktop browser emulation can verify spacing and scrolling, but cannot reproduce iOS's status-bar gradient.

## Seed a scratch database

`scripts/seed.ts` fills a scratch Hub database through the Hub's migration and ingest code. It creates four paired Systems, one unpaired System, a week of Vitals, Sessions, processes, records, runs, checks, and Harness installs. `workstation-1` has disk Conditions at all three levels, one occurrence that escalates from note through warning to alert, and a backfilled historical level. `gateway-1` has only notes, a disk note and maintenance notes, and remains healthy. `workstation-1`'s syncthing has five Service stops (a killed one received hours late, a failed restart storm, a clean one, one with an unknown result, and a failure minutes ago after one restart) and an open Service restarted note. `server-1` and `gateway-1` each have a Pending update note with security packages and a Reboot required note, and `workstation-1` a Pending update at warning. The Collector's release rolled out to three Systems 2.5 hours ago, restarting it once on each, and two of the workstation's Services have a newer upstream release. Other examples include a stopped Service, failing and overdue jobs and one that has not run yet, Drift, an unreadable file, and a Condition resting on old evidence. Reseeding resets these Systems and their transition history. The script refuses a database holding any other System. Point it at a scratch database, never a real Hub's:

```sh
HEIMDALL_DATABASE_URL=postgres://localhost/heimdall_scratch bun run --cwd packages/dashboard seed
```

## Browser interaction tests

The Service filter sheet's, the jump box's, and the System overview's DOM tests use a Chromium executable without extra packages.

HEIMDALL_TEST_BROWSER=/path/to/chromium bun test packages/dashboard/src/components/*.dom.test.ts

## Layout

- `src/main.ts`, `src/application.ts`, and `src/cli/`: the `heimdall-dashboard` command line. `main.ts` is the entry point, `application.ts` declares the command and adds the shared `service` commands, and `cli/` holds `serve`.
- `src/routes/`: pages and the API routes. `src/routeTree.gen.ts` is generated by TanStack Router; commit it, and do not edit it.
- `src/components/`: the page's components, small and each doing one thing. `src/lib/` holds the pure helpers they share (time formatting, axis ticks, lane text), each with a `bun:test` test.
- `src/server/`: server-only code. Query functions take a `SQL` and are tested against the Hub's own test harness; a server function is a thin wrapper around one.
- `src/components/ui/`: shadcn/ui components, added with `bunx shadcn@latest add <name>`. They are excluded from the repository's lint.
- `src/styles.css`: the theme, as Tailwind and shadcn CSS variables, and the Inter variable font from Fontsource. Components take every color from its tokens: three surfaces (page, bar, card, with the `card-surface` utility for a card's gradient and shadow), `link` for links, `select` for what is selected, `plot` for data that carries no level, Harness, or series (CPU and memory lines, meters, and the neutral marks of a trace, a timeline, or a breakdown), the status colors for levels, the `series` colors for breakdowns and models, and `chart-1` and `chart-2` for the Claude Code and Codex Harnesses and nothing else. Each color is written once; a token that shares it refers to the token that holds it.
- `src/components/plot-scale.tsx` and `src/lib/chart-scale.ts`: the chart primitives every CPU, memory, and Condition plot shares: the gradient under a line, the value scale's labels, and dashed limit lines. A scale is widened to whole steps (`niceDomain`) so each label states the value drawn at its position.
- `public/`: the icons, served at fixed paths. `favicon.svg` is the source. `favicon.ico` holds its 32 px render, and `apple-touch-icon.png` is a 180 px render of it as a full square, without the rounded corners and border, since iOS rounds the corners itself. Render both again when the SVG changes.

# Fleet observability spec

A fleet is a person's own set of Systems. Heimdall observes a fleet and the agent work done on it, whatever provisions its Systems. This spec states what each role does and what a provisioner follows to plug in. [ADR-0011](decisions/0011-collectors-hold-what-provisioners-record.md) and [ADR-0012](decisions/0012-hub-archives-agent-session-transcripts.md) record why. Terms are defined in the [glossary](glossary.md).

Roles and Principles describe Heimdall as designed. Sections marked _planned_ describe contracts not built yet, whose exact fields are fixed when the milestone that builds them lands ([roadmap](roadmap.md)).

## Roles

| Role | Runs | Does |
| --- | --- | --- |
| System | everywhere | One machine in the fleet, named by a DNS label. |
| Collector | on each System, as one account | Samples Vitals, holds what provisioners record, checks it, finds the installed Harnesses and their versions, watches the running Harness processes, and sends Reports and transcripts to the Hub. |
| Hub | on one System | Stores Reports and transcripts in PostgreSQL, derives Conditions, mirrors each System's records, and derives Session insight from transcripts. |
| Dashboard | on the Hub's System | Reads the Hub's database and serves every read: pages that show every System, its Vitals, records, and Conditions, and its agent Sessions, and the read API, the records read included ([ADR-0015](decisions/0015-dashboard-is-its-own-app-reading-the-hubs-database.md)). |
| Provisioner | wherever its operator runs it | Installs things on Systems and records them with each System's Collector. Fleet is one provisioner; [Running Heimdall with Fleet](fleet.md) shows how it does this. |

A System joins by pairing its Collector with the Hub once, as the [README](../README.md#pairing-a-new-system) describes.

## Principles

1. **The Collector holds what is on its System.** A provisioner tells it what it installed; the Hub mirrors that and manages nothing.
2. **Heimdall compares recorded with observed, on one System.** A recorded Service that stopped, a recorded job that missed its schedule, and a recorded file that changed are Heimdall's to report.
3. **The provisioner compares declared with recorded.** Heimdall stores no provisioner's declarations. Gaps such as declared but not installed are found by the provisioner's own check, which reads the records the Hub mirrors.
4. **Heimdall reports and never manages.** Nothing the Hub sends changes a Collector's records or what it observes.
5. **Every record is optional.** A System nobody records anything on still reports its Vitals and, from the sources it captures, its agent Sessions' transcripts.
6. **The Hub keeps agent Session transcripts** as the durable record of agent work, after each Harness deletes its own copy.

## Recording what a provisioner installed

A provisioner records something it installed by piping one JSON object to `heimdall-collector record <kind>`, and removes it with `heimdall-collector forget <kind> <name>`. It runs both as the account the Collector runs as, so the records land in that Collector's state, even when the install itself ran as another account such as root. The kinds are `application`, `service`, `job`, and `files`.

`record` reads at most 1 MiB from standard input and refuses a terminal. It exits 1, stores nothing, and names the field and the problem when the input is empty, is not JSON, fails the rules below, or carries a field the kind does not list; it never repeats the input. A mistake therefore fails the provisioner's command at once, and a field is never dropped without notice. On success it prints `Recorded <kind> <name>.` and exits 0. Recording a kind and name again replaces the record. `forget` removes the record and exits 0 with `No <kind> <name> is recorded.` when there is none, so an uninstall script can run it whether or not the install was recorded. Forgetting a job also removes its runs.

Records live in `records.sqlite` in the Collector's state directory, which `record` creates, readable by its owner alone, if it is missing. Pairing is not required. Wiping the directory loses the records, and the provisioner records them again. A new kind or supervisor is added only when a provisioner needs it.

### Fields

A name is 1 to 128 characters: letters, digits, `.`, `_`, and `-`, starting with a letter or digit. A text field is 1 to 256 characters of well-formed Unicode with no control characters. Every kind may carry `provenance`, which is optional: `by`, text of at most 64 characters, and optionally `revision`, text of at most 128. Heimdall shows it and never compares it.

| Kind | Fields |
| --- | --- |
| `application` | `name`, `version` (text of at most 128 characters), optional `source` (text), optional `provenance`. |
| `service` | `name`, `supervisor`, optional `health`, optional `port`, optional `provenance`. The supervisor decides what names the Service to it: `unit` for `systemd` and `systemd-user`, `label` for `launchd`, `container` for `docker`, and no target for `none`. A `container` is a Docker container name or ID: it starts with a letter or digit, continues with letters, digits, `_`, `.`, or `-`, and is at most 256 characters, since the Collector puts it in the path of a request to the Docker Engine and a `/`, `?`, `#`, or `%` could change that path; such a `container` is refused. A `systemd` or `systemd-user` `unit` names one unit, since `systemctl` reads a name with `*`, `?`, or `[` as a pattern that can match several units or none, and a name of only digits as a job id; such a `unit` is refused. A `launchd` `label` names one service for `launchctl print`, which reads it after `<domain>/`, so a `label` with `/` is refused. `health` is `http://127.0.0.1:<port>` or `http://[::1]:<port>`, optionally followed by a path of printable ASCII other than space, with a port from 1 to 65535; `localhost` and every other host are refused. `port` is an integer from 1 to 65535. |
| `job` | `name`, `scheduler`, `schedule`, optional `graceMinutes`, optional `provenance`. The scheduler decides what names the job to it: `label` for `launchd`, `unit` for `systemd-timer`. `schedule` lists 1 to 100 calendar entries in the System's local time, with the meaning of launchd's `StartCalendarInterval`: each entry has at least one of `minute` (0 to 59), `hour` (0 to 23), `day` (1 to 31), `weekday` (0 to 7, where 0 and 7 are both Sunday), and `month` (1 to 12), all integers, and a field left out matches every value. Two identical entries, with weekday 0 and 7 counted as equal, are refused. `graceMinutes`, an integer from 1 to 10,080, is how long the System must be awake after a scheduled time before the Hub raises job overdue; it is 60 when left out. Recording a job again keeps its runs. |
| `files` | `name`, `files` (1 to 10,000 entries of `path` and `sha256`), optional `provenance`. A `path` is absolute and normalized, at most 4096 bytes, and has no control characters: it has no empty, `.`, or `..` segment and no trailing slash, and `/` alone is not a file. Paths within a record are unique. A `sha256` is 64 lowercase hexadecimal characters. |

A job reports each run with `heimdall-collector record run <job>`, which reads one JSON object from standard input like the other kinds. The job must have a `job` record, and the command exits 1 for a run of one that has none. A run has `started` and `finished`, UTC times in ISO 8601 with whole seconds such as `2026-10-01T03:00:05Z`, where `finished` is not earlier than `started`; `exitStatus`, an integer from 0 to 255, where 0 is success; and optionally `output`, with `file`, the output file's name without any directory, and `sizeBytes`, a non-negative integer. Runs are keyed by job and `started`, so recording the same start again replaces the run. Recording a run prunes that job's runs that started more than 90 days earlier, except the job's latest successful run. A run that is itself that old, and not the latest success, is not kept: the command exits 0 and prints `Run of <job> started <started> is older than 90 days and was not kept.` instead of `Recorded run of <job> started <started>.` A job's runner should ignore a failure to record, so a broken Collector never fails the job.

### Examples

```json
{"name": "webapp", "version": "1.4.2", "source": "https://example.com/webapp-1.4.2.tar.gz", "provenance": {"by": "my-provisioner", "revision": "3f9c2ab"}}
```

```json
{"name": "webapp", "supervisor": "systemd", "unit": "webapp.service", "health": "http://127.0.0.1:8080/healthz", "port": 8080}
```

```json
{"name": "nightly-backup", "scheduler": "systemd-timer", "unit": "nightly-backup.timer", "schedule": [{"hour": 3, "minute": 30}]}
```

```json
{"name": "webapp-config", "files": [{"path": "/etc/webapp/webapp.conf", "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"}]}
```

```json
{"started": "2026-10-01T03:30:00Z", "finished": "2026-10-01T03:42:17Z", "exitStatus": 0, "output": {"file": "backup-2026-10-01.tar.gz", "sizeBytes": 73400320}}
```

The last example is the input to `heimdall-collector record run nightly-backup`.

### What Heimdall checks and reports

The Collector reports its records to the Hub, as [Reading the records back](#reading-the-records-back) describes, and checks those it can observe. The Hub raises the job Conditions described in [Job Conditions](#job-conditions), the stale System and low disk Conditions described in [System Conditions](#system-conditions), Drift as described in [Drift](#drift), and Service down as described in [Service down](#service-down). The Collector checks a Service's supervisor when it is `systemd`, `systemd-user`, `launchd`, or `docker`, and a Service's health URL when the record has one.

| Kind | Heimdall checks and reports |
| --- | --- |
| `application` | Reported as recorded; the version is not observed. |
| `service` | Supervisor state for `systemd`, `systemd-user`, `launchd`, and `docker` Services, which the Collector asks each minute; a stopped Service raises Service down. The `health` URL, when the record has one, which the Collector requests each minute and only on loopback; an unhealthy Service raises Service down too. A `none` Service with no `health` URL has nothing to check and is reported as unchecked, never as down. |
| `job` | Each run the job reports. A failed latest run raises job failing; a scheduled time followed by a grace period of awake time, with no successful run since, raises job overdue. |
| `files` | Each file's current hash, which the Collector compares with the recorded one. A file that no longer matches, or no longer exists, raises Drift. A file the Collector cannot read is reported as unreadable and raises nothing. |

A new field reaches the dashboard only when every layer knows it, so the Hub is upgraded first, then the Collectors, and only then does a provisioner send the field.

### Condition levels and history

Every Condition carries a level set by the Hub: **note** means something to know, **warning** means act this week, and **alert** means act now. Service restarted has a fixed note level. Drift and job overdue have fixed warning levels. Service down, stale System, job failing, and Reports rejected have fixed alert levels. Disk and clock skew have measured levels, as described below.

A System's health is its worst open level. Notes alone leave it healthy. Old or unknown evidence does not lower an open Condition's level. The dashboard reads the Hub's stored levels. There is no muting, acknowledgement, or snooze.

An open Condition keeps its identity, System, kind, and subject, through level changes. Its occurrence starts when raised and ends when cleared. A later recurrence starts another occurrence. The Hub stores raised, level-changed, and cleared transitions in the same transaction as the current level. Each transition carries its level, reason, and time. A level change also carries its previous level. Reason-only updates add no transition.

The Timeline groups transitions by occurrence, with the most recently raised occurrence first in recording order. Level changes never reorder occurrences. Transitions within an occurrence keep their recording order, even when their times are equal. Each transition time is at least the previous transition's time, including clearing after a clock reversal.

The level migration preserves existing occurrence IDs, kinds, subjects, times, and reasons. Legacy disk occurrences receive alert; other kinds receive their fixed levels. Their historical levels are explicitly backfilled, not observed. Normal evaluation subsequently grades existing open disk occurrences without replacing them. See [ADR-0017](decisions/0017-the-hub-sets-condition-levels.md).

### Job Conditions

The Hub judges every System's recorded jobs once a minute, from the records and latest runs it mirrors, the System's time zone, and the System's Vitals. Each job Condition is about one job and names it on the dashboard and in the Timeline.

- **Job failing** is raised when the job's latest run exited with a status other than 0, and its reason names the run's start and exit status. A later failing run replaces the reason. It clears when the latest run succeeds.
- **Job overdue** is raised when one of the job's scheduled times passed, the System was then awake for the job's grace period, and no successful run started at or after that scheduled time. Its reason names the scheduled time in the System's local time, and it clears once such a run is reported. A job can be failing and overdue at once.

Awake time is counted from the Vitals samples the Hub stored, which a Collector takes every 15 seconds while its System is awake. The Hub counts each 5-minute rollup bucket as awake for 15 seconds per sample, up to the whole bucket, and counts no bucket later than its own clock. A System asleep through a scheduled time therefore gets its whole grace period after it wakes, as does one whose Collector stopped. The Hub looks back at most 90 days; a System not awake for the grace period within them leaves job overdue as it is. Samples and runs both carry the System's own clock.

The Hub reads a schedule's entries as wall-clock times in the System's time zone. As in cron, an entry that names both `day` and `weekday` fires on either, and `month` always applies. launchd also fires on either, but ignores `month` for a weekday, so the Hub never expects a run launchd would skip. A time that a clock change skips falls as much later as the clock skips, and one it repeats falls the first time. Scheduled times count only from when the Hub first mirrored the job, so a job recorded today is not overdue for a time that passed before. Recording a job again keeps that time, and so does a record set over budget or one that lists the job as unreadable; only a set that leaves the job out forgets it.

A job Condition stays as it is while what decides it is unknown: while the System's record set or runs are over budget, while the Collector or the Hub cannot read the job's record or runs, while the System has never sent runs, and, for job overdue, while the Hub has no time zone for the System or does not know its zone. A job whose record is forgotten clears both.

## System Conditions

Once a minute, in the same pass as the job Conditions and one after the other, the Hub judges every paired System for stale System, disk, clock skew, rolling load, and update Conditions.

- **Stale System** is raised when the Hub last heard from the System more than 10 minutes ago, or more than 7 days ago when the System sleeps. Any Report counts as hearing from it, including one the Hub rejects, and so does any transcript upload. A paired System the Hub has never heard from counts from when it was paired, so a Collector that never starts is stale too. The Hub then holds a row for that System with no last seen, and the dashboard shows it as never seen. A System with a last seen counts from that time even if it was paired again since, so pairing it again does not clear the Condition. The Condition has no subject, its reason names the time the System was last heard from (or paired, if never), and it clears at the next judgment after the System is heard from again. The Hub does not count time it was not listening: it records that it listens every 30 seconds, and after a gap of more than 2 minutes, such as an outage of the Hub or its database, it raises stale System only once it has listened for 10 minutes again, whether or not the System sleeps, which gives Collectors time to send what they queued. Until then an open stale System stays open, and only hearing from the System clears it. A quick restart leaves no such gap.
- **Low disk** is graded per mount: note at 70% used, warning at 80%, and alert at 90%. Raising or escalating includes equality. Recovery uses a five-percentage-point margin: alert steps down below 85%, warning below 75%, and note clears below 65%. Equality retains the level. A large change moves directly to the resulting level or clears, without fabricated intermediate transitions. The subject remains the mount and the stored kind remains `low_disk`. Its latest reason gives free space, such as `9.9 GiB free of 100.0 GiB (9.9%).` A mount missing from a fresh sample clears. A sample older than two hours cannot lower or clear an open disk Condition, including a missing mount. A mount with a size of 0 is left as it is. Duplicate mounts use the entry with the least free fraction, then least free bytes. A System with no readable sample is not judged for disk.
- **The latest sample** is the newest one stamped no later than 5 minutes after the Hub's clock, since the Hub does not store when it received a sample, and a System whose clock runs ahead would otherwise keep its newest, wrongly stamped sample as the latest for as long as the clock is wrong.
- **A System that is no longer paired** is no longer judged for stale System, disk, clock skew, rolling load, or updates, and the next judgment clears those Conditions. Its other Conditions and its history stay. Its job, Drift, and Service down Conditions stay open, since no new Report arrives to change what they are judged on, and they show in the status of the dashboard's unpaired view. They change again only once new Reports arrive after it is paired again.

Disk limits are percentages in `[conditions.disk]` in `hub.toml`, or the equivalent JSON `conditions.disk` object. All fields are optional: `note = 70`, `warning = 80`, `alert = 90`, and `hysteresis = 5` are the defaults. `[conditions.systems.<System>.disk]` overrides individual fields for that System, inheriting unspecified fleet limits. `hysteresis` is a positive number of percentage points. Limits must satisfy `0 < hysteresis < note < warning < alert <= 100`, with each adjacent level gap greater than hysteresis. Unknown settings, invalid System names, invalid values, and invalid inherited combinations stop `serve` before it opens the database. Fixed levels cannot be configured. Changed limits take effect after restarting the Hub and change subsequent judgments, never recorded history. Stale time limits retain their fixed defaults.

The Collector says whether its System sleeps with `sleeps = true` in `collector.toml`, `--sleeps`, or `HEIMDALL_SLEEPS`, and false when left out, and puts that in every Report as the boolean `sleeps`. The Hub stores the latest value it received. A Report without `sleeps`, from a Collector that predates it, leaves the stored value as it is, and so does one whose `sleeps` is not a boolean, which the Hub drops without rejecting the Report. A System that has never sent it counts as always on. Upgrade the Hub, then the Collectors: a laptop whose Collector predates `sleeps` is stale after 10 minutes until it is upgraded and configured.

### Clock skew

A System whose clock disagrees with the Hub's is a problem before its data is lost: once its samples are stamped more than 5 minutes ahead of the Hub's clock, the Hub skips its newest samples when judging disk, load, and hot processes. **Clock skew** (`clock_skew`) is a graded Condition that the Hub raises well before that point. Its subject says whose clock is wrong: empty when the System's own clock disagrees with the Hub's, and `hub` when the Hub's clock is wrong, raised on the one System that shares it. A System holds at most one of the two at a time.

- **Measuring.** The Hub reads its own clock when a Report request arrives, before it reads the body, so the time a large backlog Report takes to upload never counts as skew. The offset is the Report's `sentAt` less that time, positive when the System's clock is ahead. The Collector stamps `sentAt` on each Report as it sends it, including a resend of a Report the Hub refused, so a Report queued while the Hub was away still measures the clock at the time it arrives. The Hub keeps only the latest offset of each System, with the time it judged it. A Report the Hub rejects records none.
- **Levels.** Either direction counts. A skew of at least 30 seconds is a note, 120 seconds a warning, and 300 seconds an alert. Escalation is immediate. Stepping down or clearing waits until the skew is 5 seconds below the limit it leaves, as for disk, so a note clears below 25 seconds, and a drop can skip levels. The reason reads `Its clock is 42 s ahead of the Hub's.` or `behind`.
- **Freshness.** The Hub judges only offsets it recorded within the last 10 minutes of its own clock. A System with no such offset, such as one whose Collector stopped, keeps its Condition as it is, neither raised, re-levelled, nor cleared. Stale System covers a Collector that stays quiet.
- **When the Hub's clock is wrong.** A Hub whose clock is off puts every System off alike, except the one whose Collector shares that clock. A System within 5 seconds of the Hub reads true, and every other System is off. When exactly one System reads true and at least two are off, with the off Systems' offsets all within 5 seconds of one another, the Hub blames its own clock. Distance from the Hub classifies the Systems, not the note limits, so the rule neither flaps while the Hub drifts through a limit nor lets a System recovering inside its hysteresis band count as true. The Hub raises clock skew with subject `hub` only on the System that reads true, and clears its own-clock Condition there. The reason names the Hub's offset, the negated median of the off Systems' offsets, and how many Systems agree, such as `The Hub's clock is 3 min 2 s ahead of 3 other Systems.` The level comes from that offset against the System's limits, with hysteresis from the level its `hub` Condition holds, so a Hub under the note limit is blamed but raises nothing. The rule raises none on the agreeing Systems and clears any they hold at once. When the blame ends, the `hub` Condition clears and the System is judged on its own offset again. With only one other System off, with no System reading true, with two reading true, or with off Systems that disagree by more than 5 seconds, each System is judged alone on its own offset. The rule cannot tell which Collector shares the Hub's clock, so when the Hub's System runs no Collector and two Systems are wrong alike while a third is right, the Hub blames the right one; only naming the Hub's System would avoid that.
- **Unpairing.** A System that is no longer paired has its clock skew Condition cleared at the next judgment.

Clock skew limits are seconds in `[conditions.clock]` in `hub.toml`, or the equivalent JSON `conditions.clock` object. All fields are optional: `note = 30`, `warning = 120`, `alert = 300`, and `hysteresis = 5` are the defaults. `[conditions.systems.<System>.clock]` overrides individual fields for that System, inheriting unspecified fleet limits. Limits must satisfy `0 < hysteresis < note < warning < alert`, with each adjacent level gap greater than hysteresis. Invalid values and combinations stop `serve` before it opens the database, as for disk. Changed limits take effect after restarting the Hub and change subsequent judgments, never recorded history.

### Sustained and recurring load

The Hub counts measured busy time within rolling windows, so sustained work and recurring bursts can both qualify:

| Condition | Busy reading | Busy time | Window | Level |
| --- | --- | --- | --- | --- |
| High CPU (`high_cpu`) | Above 90% | 30 minutes | 60 minutes | note |
| High CPU (`high_cpu`) | Above 90% | 120 minutes | 240 minutes | warning |
| High memory (`high_memory`) | Above 90% on Linux; pressure on macOS | 30 minutes | 60 minutes | warning |

Both Conditions have an empty subject and name their resource in their reason.
The CPU percentage covers all cores. Equality with the percentage limit does not count as busy.
Duration equality qualifies. Reasons give the measured busy minutes, the window, and its ending sample time.
A quiet newest reading can leave a qualifying pattern in its window.

Each sample bounds an interval ending at its timestamp.
The interval counts at most 15 seconds and no more than either the time since its predecessor or the increase in uptime.
A first sample, a gap over 30 seconds, or a non-increasing uptime contributes no known interval.
Timing jitter and whole-second uptime can make this count conservative, delaying qualification beyond the same elapsed wall time.
Missing intervals remain unknown. Sleep, a reboot, and a quiet Collector never create busy time.
Windows end at sample time, not the Hub's wall clock. Samples more than five minutes ahead of the Hub are left for a later pass.

Linux memory use subtracts the kernel's `MemAvailable`, so reclaimable cache is already excluded.
On macOS, a sample is busy when its `memory.pressure` is `warning` or `critical`, whatever its use; the memory percentage applies to Linux only.
Live macOS readings showed pressure rising at 70 to 80% used, so a usage limit would hide it.
The Collector reads `kern.memorystatus_vm_pressure_level` with a read-only `sysctl` query, mapping 1 to `normal`, 2 to `warning`, and 4 to `critical`.
These values follow [XNU's pressure notification mapping](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus_notify.c).
The optional field keeps Report schema version 1.
An unavailable probe or an unknown pressure value omits pressure and preserves the other Vitals.
A macOS sample without pressure is unknown for this judgment. A normal pressure reading is known non-busy evidence.
A zero memory total is unknown. Older samples without a recorded platform cannot establish high memory use.

Raising and escalation require enough measured busy time.
A new current Condition also requires a latest sample no older than two hours.
Old backlogs can add completed historical episodes while incomplete old episodes wait for fresh evidence.
An open level is retained while unobserved intervals could still make that level qualify.
Recovery therefore requires enough known non-busy time to rule out the old level, even if every unknown interval were busy.
CPU can step down from warning to note or clear. A latest sample older than two hours cannot lower or clear an existing current Condition.
Historical replay still records already completed episodes from an old backlog.
A quiet Collector alone does not move a window or change the judgment.
If a clock rollback leaves every eligible sample behind the evaluated cursor, current judgments hold until the sample timeline catches up.

The Hub replays newly stored readings in sample order and records qualifying episodes even when later readings in the batch establish recovery.
Transitions use the Hub's evaluation time, following ADR-0017. Their reasons identify the sampled window.
A durable per-System cursor commits with the Conditions, preventing repeated evaluation or Report retries from recreating completed episodes.
Newly stored readings behind that cursor mark the System for historical replay. Sample-time spans identify recorded episodes, so replay adds unseen completed episodes without duplicating overlapping history or changing a later open occurrence.
On first evaluation, the Hub scans the raw samples it still holds. Raw retention bounds retrospective detection.
An unfinished historical episode keeps a pending sample-time boundary across evaluation passes.
Later batches replay from before that boundary until observed recovery records the episode, including when an old backlog meets fresh quiet samples.
The Hub stores whether the latest evaluated CPU and memory intervals were known.
The dashboard uses that coverage only when it matches the newest sample, keeping unknown evidence distinct from the stored level.
Only raw samples carry pressure. Existing Vitals rollups and insight views keep their current shape.

Load limits live in `[conditions.cpu]` and `[conditions.memory]` in `hub.toml`, or the equivalent JSON objects.
CPU fields default to `percent = 90`, `noteMinutes = 30`, `noteWindowMinutes = 60`, `warningMinutes = 120`, and `warningWindowMinutes = 240`.
Memory fields default to `percent = 90`, `warningMinutes = 30`, and `warningWindowMinutes = 60`.
These defaults were checked against 12 days of live readings from four Systems: they raised one CPU note, during several hours of sustained build work, and no warnings.
`[conditions.systems.<System>.cpu]` and `[conditions.systems.<System>.memory]` override individual fields, inheriting the rest.
Percentages must be greater than zero and at most 100. Durations and windows range from 0.25 to 18,720 minutes, within raw retention.
Each duration must fit its window. CPU's note duration must be less than its warning duration, and its note window cannot exceed its warning window.
Unknown fields and invalid inherited combinations stop `serve` before it opens the database.
Restarting the Hub applies changed limits to subsequent judgments, including its latest stored window, without rewriting recorded history.

### Hot processes

The Hub raises `hot_process` for an individual process above 0.5 CPU core for 30 measured minutes within an hour at note,
or 120 measured minutes within four hours at warning.
One core means one CPU second per elapsed second, regardless of the System's core count.
Equality with the core limit is quiet. Duration equality qualifies.
Only the process's own user and system CPU time counts, excluding descendants and reaped children.
Each subject identifies a boot, PID, exact kernel lifetime identifier, and reported executable name. Separate lifetimes never share busy time.
Reasons and dashboard labels name the executable and PID.

The Collector shares one process-table pass with Harness tracking per Vitals sample.
An optional `processes` field carries the five hottest measured processes, each with its executable name, PID, lifetime identifier, CPU cores, and resident bytes.
It never carries arguments or environment variables.
Executable lookup falls back to the platform's accounting name when unreadable, which can be truncated.
The first reported fallback name stays attached to that lifetime, so changing an accounting name or losing read permission cannot clear a still-hot process.
The Collector keeps these names and confirmed executable names in `process-names.sqlite` under its configured state directory.
Collector restarts preserve those labels while discarding CPU baselines. Confirmed absence, replacement, or a new boot removes the old name.
Only a change between two confirmed executable names establishes an executable replacement.
An empty or invalid name leaves that PID unknown without discarding other processes.
Linux uses its boot ID and kernel start ticks. macOS uses `kern.bootsessionuuid` and libproc's full 64-bit process unique identifier.
XNU exempts `PROC_PIDUNIQIDENTIFIERINFO` from the same-user check, allowing root-owned processes to be observed without the privileged BSD start-time query.
The [kernel access policy](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/proc_info.c) and [API structure](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/proc_info_private.h) define this query.
A denied unique-identifier query leaves that process unknown.
CPU rates use monotonic elapsed time. A baseline, a counter decrease, changed identity, or invalid interval contributes no busy time.
Credited intervals cannot exceed 15 seconds, the monotonic interval, the wall-time interval, or the increase in uptime.
A wall-time or monotonic gap over 30 seconds is unknown. Failed probes omit process evidence while preserving host Vitals.
Harness tracking consumes a successful table read even when host Vitals fail.
A host Vitals read has a 15-second deadline. A timed-out read stays the only host read in flight until it settles, and its late result is discarded.
Later sampling attempts still read processes while that host read is pending.

A complete census includes every enumerated PID, unreadable PIDs, and the highest measured CPU rate omitted from the top five.
An omitted process is known quiet only when its PID was readable and the omitted ceiling does not exceed the Hub's core limit.
Otherwise its CPU is unknown. Absence from the top five alone never establishes recovery or exit.
Each census list is limited to 4,096 PIDs. Overflow makes the census partial, disabling absence and omitted-quiet inference.
Top-five readings remain usable with a partial census.
Report delivery splits batches by encoded bytes as well as sample count, preserving the Report size cap.

Measured busy time, unknown intervals, freshness, level changes, historical replay, and recovery follow the load rules above.
An alive process can step down or clear after enough measured quiet time rules out its held level.
A fresh complete census that no longer contains its PID confirms exit and clears immediately.
A changed boot, a replacement lifetime identifier, or a confirmed executable replacement also ends the previous subject.
A present PID outside the top five does not confirm reuse. Its earlier lifetime can remain uncertain until replacement or absence is observed.
Old evidence cannot lower or clear a current Condition, including by exit.
The Hub stores coverage for each subject, and the dashboard uses it only when it matches the latest Vitals sample.
A quiet Collector, missing fields from older Collectors, and unreadable processes never establish recovery.

`[conditions.process]` configures `cores = 0.5`, `noteMinutes = 30`, `noteWindowMinutes = 60`,
`warningMinutes = 120`, and `warningWindowMinutes = 240` by default.
`[conditions.systems.<System>.process]` overrides individual fields, inheriting the rest.
The core limit must be finite and positive. Durations and windows use the load bounds and ordering rules above.
Invalid inherited combinations stop startup before database access. Restarting the Hub applies changed limits without rewriting history.
Process evidence remains in raw Vitals samples and does not change Vitals rollups or Session insight.

## Update Conditions

The Collector observes package-manager metadata independently of provisioner records, following [ADR-0018](decisions/0018-collector-checks-package-managers-on-a-schedule.md).
It never installs software, refreshes repository metadata, changes ownership, or reboots a System.
A provisioner's Application records retain their recorded versions.

Checks run at startup and every six hours after the preceding pass finishes, independently of Vitals and Report delivery.
They never overlap or replay intervals missed during sleep.
`[updates]` in `collector.toml`, or its JSON equivalent, accepts `intervalHours = 6` by default.
The interval must be finite, at least one second (`1/3600` hours), and at most 596 hours.
Local path settings are `apt`, `aptListsDir`, `dpkgQuery`, `osRelease`, `rebootMarker`, `homebrewPrefixes`, and `homebrewCacheDir`.
Paths must be absolute. Homebrew prefixes list at most 14 distinct installations.
The defaults use standard operating-system locations and the Collector account's Homebrew cache.
Removing a prefix from configuration does not prove that its packages were uninstalled.

On Debian-family Linux, APT lists upgradable packages using existing local package indexes, with a separate complete `dpkg-query` census of installed packages.
APT identities include package architecture.
A security suite explicitly named by APT establishes security status. Other packages retain unknown security status.
Missing indexes, malformed output, command failure, or inaccessible metadata produce unavailable coverage, never an empty successful list.
The metadata timestamp is the oldest local package-index modification time, not the time Heimdall queried it or proof of a recent refresh.
The Debian-family reboot-required marker reports an already required reboot. Its absence on another operating system establishes nothing.

Homebrew coverage requires the Collector account to own the installation.
The Collector reads installed receipts and verifies cached signed API metadata locally, without running Homebrew or triggering its network fallback.
Unsupported cache layouts, receipt provenance, or version comparisons produce unavailable coverage.
A separate account requires a different execution arrangement before it can be observed. The Collector performs no automatic account switching.
macOS Software Update coverage remains unavailable because no supported cache-only query has been verified.
A pending operating-system update that requires a restart is distinct from an already required reboot.

### Report evidence and freshness

The optional v1 `updates` section carries `managers` and `reboot`, bounded to 1 MiB of JSON.
Each manager identifies its `manager` and `installation`, retains `observedAt`, and carries an available or unavailable `result`.
An available result holds `metadataAt` and pending `updates`, each with `name`, `installed`, `available`, and `security`.
Unknown versions, metadata age, and security status are `null`.
An optional complete `installed` census carries its own `observedAt` and package `names`.
Its optional `versions` entries carry a package `name` and confirmed fully installed `version`; every entry names a package in the census.
Partly installed or partly configured packages remain present in `names` but have no confirmed installed-version entry.
The reboot observation carries `observedAt` and either an available `required` boolean or an unavailable reason.
The schema lives in `packages/schema/src/updates-section.ts`.

The Collector sends changed observations and repeats them hourly using their original observation times.
Failed delivery retries the section. Resending a cached observation does not make it new evidence.
An oversized observation becomes unavailable coverage, with no truncated successful package list or census.
The Hub orders observations independently per manager installation and for reboot-required, ignoring repeated or older observations.
After unpairing withdraws a Condition, re-pairing can reconfirm an identical cached observation with a new pending age.
Evidence more than five minutes ahead of the Hub's clock is ignored.

Repository-based recovery requires a successful query observed within 24 hours and known metadata no older than seven days, including equality at both boundaries.
A complete local census observed within 24 hours can independently prove that a previously pending package was uninstalled.
The same census can prove installation of the previously reported candidate when its confirmed installed version exactly matches that candidate.
This evidence does not depend on repository metadata age or on a successful repository query.
The census must be at least as recent as the package's last positive observation.
A newer observation still listing the package as pending prevents either local recovery inference.
An unknown candidate or installed version cannot prove installation.
An installed version that differs from the previous candidate, including a newer version, cannot use this recovery exception.
Unknown, stale, failed, inaccessible, missing, disabled, or unsupported evidence alone cannot clear or lower an open update Condition.
Metadata maintenance remains outside the Collector, so a quiet update list is not proof that a System is current.

### Identity, age, and clearing

The Hub raises and grades update Conditions once a minute under each System's lock.
It commits fresh recovery and clearing with the Report, so a later observation cannot erase recovery before the next judgment.
`pending_update` has the subject `JSON.stringify([manager, installation])`: one Condition for each package source on a System, however many packages are pending in it.
The Hub keeps one row of evidence for each pending package, with its own security age, and the Condition's reason counts them, such as "6 APT packages are out of date, 2 of them are security updates."
A package joining or leaving the source changes the reason's counts and preserves the open occurrence and its pending age. A newer candidate version keeps the occurrence and its age; it changes the reason only when it changes the security count.
Ordinary pending updates raise notes. A source is a warning when any of its packages is a confirmed security update that has waited more than three calendar days; otherwise it is a note.
The security age of a package starts when the Hub first receives positive security evidence for it, rather than a package release date or a backlogged observation's time.
Unknown security evidence preserves an established security age.
Fresh evidence explicitly identifying a pending update as non-security can reset that package's age.
An open warning is lowered only when no package qualifies and fresh evidence establishes the security of every package left in the source.

`reboot_required` has an empty subject. It raises a note and becomes a warning after more than seven calendar days from Hub confirmation.
Sleep and a quiet Collector do not pause either age.
The defaults are `securityWarningDays = 3` and `rebootWarningDays = 7` in `[conditions.updates]` in `hub.toml`.
`[conditions.systems.<System>.updates]` overrides individual fields and inherits the rest.
Each value must be finite, positive, and no greater than 3650 days. Restarting the Hub applies changed limits without rewriting history.

A fresh successful update list that omits a pending package removes that package from its source, and the Condition clears with the last package it lists.
Authoritative fresh local proof of uninstallation or exact installation of a package's previously reported candidate also removes it.
A fresh explicit absence of the Debian reboot-required marker clears reboot-required.
A missing executable, removed configuration entry, failed lookup, or lost installation access does not establish subject removal.
Database migration 30 merged each System's open per-package occurrences into one for each source: the earliest-raised occurrence stayed open under the source subject at the worst level of the group, and the rest closed with a note that they were merged.
Unpairing clears update Conditions at the next judgment. A later recurrence starts a new occurrence and age.
The dashboard uses stored Hub levels and dates update evidence independently of Vitals and Last seen.

## Drift

The Collector hashes every file in its `files` records with SHA-256 when it starts, right after the `files` records change, and an hour after the last time it hashed them. Recording a run, an application, or the same `files` record again does not start a pass. It follows symbolic links and hashes one file at a time, reading each as a stream, so a large file is never held in memory, and reading no more than the file's size when it opened it, so a file that keeps growing cannot stall a pass. It reads no file a provisioner keeps as its own record, and hashes only the paths its own `files` records name. A pass stops between chunks when the Collector stops. A read that hangs, as on an unreachable network mount, cannot be cancelled and holds the pass until the operating system returns. Each file is in one of four states:

- **Matching**: the content hashes to the recorded value.
- **Drifted**: the content hashes to another value.
- **Missing**: no file exists at the path, including a symbolic link whose target does not exist, or a path under something that is not a directory.
- **Unreadable**: the Collector could not read the content, such as when permission is denied, when the path is a directory, a device, or a named pipe, or when symbolic links loop.

The Collector reports every file that is not matching in the `checks` section described under [Reading the records back](#reading-the-records-back), with the record that names it, the state, and `since`, the Collector's clock when it first saw the file in that state. A file that stays in one state keeps its `since` for as long as the Collector runs, and one that changes state takes the time of the pass that saw it. A restart forgets `since`, so a file still mismatched then takes the time of the first pass after it. The section also lists, for each `files` record the pass hashed, the record's name and its digest.

A record's digest is the SHA-256, in lowercase hexadecimal, of its files in path order, compared by UTF-16 code unit, each written as the path, a NUL byte, the recorded `sha256`, and a newline. The order in which the provisioner listed the files does not matter. A record and the checks about it reach the Hub apart, so the Hub computes the digest of each `files` record it mirrors and trusts the Collector's verdict on the record only when the checks list the record with the same digest. A record the checks do not list, or list with another digest, has not been judged as the Hub knows it, and every path it names is unknown.

The Hub judges every System's checks once a minute, in the same pass as the [job Conditions](#job-conditions) and the [System Conditions](#system-conditions), after them. Drift is one Condition per path, whichever records name it, and its subject is the path.

- **Drift** is raised for a path that a judged record names and the checks list as drifted or missing. Its reason says whether the file changed or is missing, and names the first such record by name, compared by code unit; the Condition takes the new reason when the file goes from one to the other. A path several records name is raised if any judged record shows it drifted or missing.
- **Drift clears** when every record that names the path was judged and shows the file matching, and when no `files` record the Hub mirrors names the path at all, which is how forgetting a record clears its Drift. Neither clears while any `files` record is unreadable.

Drift stays as it is while what decides it is unknown: while the Collector reports the path unreadable, for the paths of a record the checks did not judge as the Hub mirrors it, while the System's record set is over budget, while the System has never sent checks, and while any `files` record is unreadable, whether the Collector could not read it or the Hub does not know its shape, since that record may name the path. While a `files` record is unreadable no path's Drift clears, though a path a judged record shows drifted or missing is still raised. A files part over budget judges no record, so it leaves every path a record names as it is, but a path no record names clears, so forgetting a record clears its Drift even then. A Condition raised for a path the Collector can no longer read therefore stays open until the Collector reads it again, or the record is forgotten, which clears it only while no `files` record is unreadable.

## Service down

The Collector checks every `service` record once a minute, in a loop of its own, so the hourly file hashing never delays it. A Service has a supervisor check, and a health check beside it when its record has a `health` URL, so one Service can fail two ways. Each check is in one of five states:

- **Up**: the supervisor says the Service is running, or the health URL answered with a 2xx or 3xx status.
- **Stopped**: the supervisor says it is not running.
- **Unhealthy**: the health URL did not answer with a 2xx or 3xx status, or did not answer at all.
- **Unknown**: the Collector could not ask the supervisor, or got no answer; or the Collector could not make the health request, as when it has run out of file descriptors.
- **Unchecked**: the Collector has nothing to check, which holds for a `none` Service with no `health` URL.

For a `systemd` Service the Collector runs `systemctl show --timestamp=us+utc --property=ActiveState,SubState,LoadState,NRestarts,ActiveEnterTimestamp,ActiveExitTimestamp,Result,ExecMainStatus -- <unit>` and for a `systemd-user` Service the same with `systemctl --user`, so the first asks the system manager and the second the account's user manager. The states decide the check; the other properties are what the Collector logs [Service stops](#service-stops) from. `--timestamp=` needs systemd 247 or later. It runs `systemctl` by absolute path, from the first of `/usr/bin`, `/bin`, and `/usr/local/bin` that has it, since a launchd agent or a systemd service has a minimal PATH, and gives it 5 seconds before it kills it. An `ActiveState` of `active` is up, including a unit that exited and remains. Any other `ActiveState` is stopped, including `activating`, which a unit that fails and restarts shows between attempts, and so is a unit systemd does not know (`LoadState=not-found`). A check is unknown when `systemctl` cannot reach the manager, as when the account has no user bus (the error says it failed to connect to the bus, or that systemd was not booted), when it exits non-zero for any other reason, when it times out or cannot run, when it is not installed, or when its answer lacks the states asked for or is not about exactly one unit. A stopped Service is therefore never confused with one the Collector could not ask.

For a `launchd` Service the Collector runs `/bin/launchctl print <domain>/<label>`, first in `gui/<uid>`, the GUI login domain of the Collector's account, and then in `system` if the first does not have the label, giving each 5 seconds. Only an agent loaded in that GUI domain and a daemon loaded in the system domain are found: an agent bootstrapped into `user/<uid>`, or into another account's domain, reads as not loaded. A label with a running process is up: `state = running` in the service's own fields, or a `pid` of digits. A label that is loaded with no running process is stopped, and its detail gives launchctl's `state` and, when it prints them, the `last exit code` and `last terminating signal`, such as `state = not running, last exit code = 78`; this includes an agent that launchd is holding back after it exited. A label neither domain has loaded is stopped with the detail `not loaded`. launchctl means a domain does not have the label only by exit status 113 together with the message "Could not find service", on either output stream and in any case; `service status` reads it the same way. A check is unknown for any other failure: another exit status, whatever it printed, a timeout, a launchctl that cannot run (it is not on a Linux System), output with no `state` for the service, or an account with no user id. A domain that fails to answer makes the check unknown without asking the next, since the label may be loaded there. So when the Collector's GUI domain itself cannot be asked, as for a Collector running as root or on a System with no GUI login session, every launchd check is unknown and the system domain is not asked. A `launchd` `label` may not contain `/`, since `launchctl print` reads it as part of the target; such a record is refused.

A `launchd` `service` record is for an agent or daemon meant to stay running, one with `KeepAlive`. An agent that launchd starts on demand or on a schedule, and is idle between runs by design, reads as stopped and raises Service down. Record such an agent as a `job`, or as a Service with `supervisor: none` and a health URL.

For a `docker` Service the Collector asks the Docker Engine API of its own account, which is rootless Docker by default, with no `docker` CLI: `GET /containers/<container>/json` over the Engine's unix socket, with the container name percent-encoded, no redirect followed, at most 1 MiB of the answer read, and 5 seconds to answer. The socket is the one in `DOCKER_HOST` when that is a `unix://` URL with an absolute path; otherwise `docker.sock` in `XDG_RUNTIME_DIR`, when that is an absolute path; otherwise `/run/user/<uid>/docker.sock` for the account's own uid. The Collector reads these from its own environment and never reads Docker's configuration. A provisioner whose containers run under another daemon, such as rootful Docker or Podman, sets `DOCKER_HOST` in the Collector's service environment. There is no `/var/run/docker.sock` fallback: the rootful daemon is another daemon, and it answers 404 for containers the account's own Engine runs, which would read as a false down. A `DOCKER_HOST` that names another transport (`tcp://`, `ssh://`, or a relative socket path) makes the check unknown, with a detail that says so.

The recorded `container` is the container's name without the leading `/` that the Engine shows in its `Name`, and a name is better than an ID, since an ID changes when the container is recreated. A container whose state is `running` is up. A container that is `exited`, `created`, `paused`, `restarting`, or `dead` is stopped, with a detail such as `status exited, exit code 137`, where the exit code is given for `exited` and `dead` only; the status decides paused and restarting, which the Engine also reports as running. An answer counts only when it is for the container asked for: its `Name` is `/<container>`, or the recorded value is 12 to 64 lowercase hexadecimal digits and the answer's `Id` starts with it, since the Engine also looks a name up as an ID prefix and can answer for another container. An answer for another container is stopped, with the detail `no such container`, as is a 404 whose JSON `message` says no such container (Docker and Podman both do); a 404 that does not say so, such as a proxy's `page not found`, is unknown. A socket that is missing, refuses the connection, or denies permission, a timeout, a redirect or any other HTTP status than 200 and 404, an answer over the size cap, and an answer that is not JSON with a boolean `State.Running` are unknown. Docker's own `HEALTHCHECK` (`State.Health`) is not read; the health URL covers health.

The health check requests the record's `health` URL with a `GET`, at the same time as the supervisor check. The URL is limited to loopback when it is recorded, the Collector ignores any proxy setting in its environment (`HTTP_PROXY`, `http_proxy`), and it does not follow a redirect, so the request goes to that address and nowhere else. It gives the URL 5 seconds to answer. A 2xx or 3xx status, a redirect included, is up. Any other status, a refused or reset connection, an answer that is not valid HTTP, or no answer in 5 seconds is unhealthy, with a `detail` such as `HTTP 503`, `connection refused`, `connection reset`, `invalid response`, or `timed out after 5 s`. A request the Collector could not make for its own reasons says nothing about the Service, so that check is unknown. The Collector discards the response body without reading it, and sends no credential. A `none` Service has no supervisor to ask, so its health URL is its only check, and the Collector sends no supervisor check for it; with no `health` URL it sends one unchecked supervisor check.

Each check carries its state, a short `detail` of at most 200 characters, such as `ActiveState=failed`, `LoadState=not-found`, or `bus unavailable`, and `since`, the Collector's clock when it first saw the check in this state. The Collector reports them in the `services` part of the [checks section](#reading-the-records-back), which it sends again only when a check's state or detail changes and hourly like the rest of the section, so a Service that stays in one state causes no resend. A restart forgets `since`, and so does a pass that cannot read the records, which also leaves the services part out of the section until a pass works, so the Hub holds what it has. A Service recorded again under another supervisor or target starts a new `since`.

The Hub judges Service down once a minute for every System, in the same pass as the other Conditions and after Drift. It is one Condition per Service, whatever checks the Service has, and its subject is the Service's name.

- **Service down** is raised for a Service the Hub mirrors a record for once any of its checks has been failing, stopped or unhealthy, for 2 minutes. Its reason says why the Service is down, such as `Stopped: ActiveState=failed.` or `Unhealthy: HTTP 503.`, and names the first check that has failed for 2 minutes, the supervisor check before the health check, so a Service whose two checks both fail has one Condition and a reason that does not depend on the order of the Report; a Condition that stays open takes the newer reason when it changes. The Hub counts the time a check has been failing as awake time, the way [job overdue](#job-conditions) counts the awake time after a scheduled time, but per 15-second Vitals sample: 15 seconds for each sample the System took after the check's `since`, from the raw samples the Hub keeps. A check that has failed for 8 samples has failed for 2 minutes, wherever `since` falls in a 5-minute rollup bucket. Samples and `since` are on the System's own clock, so the Hub's clock is never compared with it and counts for nothing, and a System whose clock is off by a steady amount is judged as right as one whose clock is exact; a clock stepped while a check is failing shifts the count by the step. Samples a System stamped ahead before its clock was set back still count, so a check that starts failing soon after such a correction can be raised early. A quiet Collector and sleep add no samples, so they add no time: a System that goes quiet after a Report that said stopped raises nothing however long it stays quiet, and one that wakes after sleeping through most of the 2 minutes is not raised until it has been awake for the rest.
- **Service down clears** when every check the Collector made passes, and when no `service` record the Hub mirrors names the Service, which is how forgetting a record clears it. Forgetting does not clear it while any `service` record is unreadable, whether the Collector could not read it or the Hub does not know its shape, since that record may be the Service. A cleared Service down stays in the System's history until [`heimdall-hub purge service`](#purging-a-forgotten-service) deletes it.

Service down stays as it is while what decides it is unknown: while any of the Service's checks is unknown and no other check has failed for 2 minutes (a health URL that has failed for 2 minutes raises Service down even while the supervisor check is unknown, since the failure is direct evidence), while a check that fails has not yet failed for 2 minutes of the System's awake time, while a Service has only unchecked checks, while the System has never sent checks or its checks carry no `services` part (a Collector older than Service checks), while the `services` part is over budget, and while the System's record set is over budget. A `files` part over budget does not stop Services from being judged. A check for a Service the Hub mirrors no record for is not judged.

## Service stops

A Service can stop and run again between two checks, or within the 2 minutes Service down waits, and leave no failed check behind. The supervisor still holds what happened, so at each check the Collector also compares the supervisor's own facts with a baseline it keeps per Service, and logs each stop it finds ([ADR-0021](decisions/0021-the-collector-logs-service-stops-and-the-hub-raises-a-note.md)). The Collector logs stops of `systemd` and `systemd-user` Services.

For a systemd unit the facts are the time the unit last entered its running state (`ActiveEnterTimestamp`) and last left it (`ActiveExitTimestamp`), its automatic restart count (`NRestarts`), and how its last run ended (`Result`, such as `success`, `exit-code`, or `signal`, and `ExecMainStatus`, the main process's exit status or signal number). The baseline is the facts of the last check that read them, and the boot they came from, which the Collector reads from `/proc/sys/kernel/random/boot_id`. It is kept in `stops.sqlite` in the Collector's state directory, apart from the records, so a Collector restarted within one boot compares its first check with the baseline it kept, and finds a stop that happened while it was down.

- **A stop** is a check whose unit left its running state at another time than the baseline holds. It is logged with `stoppedAt`, when the unit left its running state, and `startedAt`, when it ran again. A stop still under way at the check is logged at once with `ongoing` true and no `startedAt`; later checks that still see the unit stopped carry its restarts and latest result into the same stop, and the check that sees the unit running again ends it. A check logs at most one new stop per Service, so a restart storm logs at most one stop a minute, each with the restarts since the check before, and two stops within one check read as one, since systemd counts only automatic restarts.
- **The result and exit status** are those of the last check that saw the unit stopped. systemd forgets both when the unit starts again, so a stop that began and ended between two checks is logged with neither.
- **`restarts`** is how many automatic restarts systemd counted during the stop. A count lower than the baseline, as after `systemctl reset-failed`, becomes the new baseline, and only the times decide whether a stop happened.
- **No stop is inferred** when the Service has no baseline yet, as at its first check; when the boot differs from the baseline's, so a reboot is no stop of every Service; when the check is unknown, or `systemctl` answers a time in another form, which leaves the baseline as it was; and when the boot cannot be read. A stop under way when the System rebooted, or when its record was forgotten, ends with no known `startedAt`. A health check never logs a stop, and neither does a `none` Service.

The Collector keeps a stop until a Report carrying it is delivered, as [Reading the records back](#reading-the-records-back) describes, and keeps at most 1,000 stops per Service of those the Hub has not taken, each for 7 days after it last changed, so a long stop that has just ended is still sent; a stop under way is kept until it ends. A stop log the Collector cannot open or write costs the stops, never the Service checks or the Vitals, and is warned about. Service down still decides whether a Service is down, and its 2 minutes are unchanged.

The Hub stores each stop by System, Service, and `stoppedAt`, with the Report's `sentAt` and the Hub's received time. Each view replaces every field of that stop, including nulls, in the Report's transaction. A view replaces the held one only when the held `sent_at` is no later than the incoming one, or later than the Hub's received time. This guard keeps newer evidence when an older Report arrives, and lets a corrected clock replace future-dated evidence. The dashboard reads the held stops through `GET /api/v1/service-stops`, apart from the records read described below.

Once a minute, after Service down, the Hub judges Service stops under each System's row lock, for every System that holds a stop or an open note, paired or not. **Service restarted** is one Condition per System and Service, with the Service's name as its subject and a fixed **note** level. The note stays open for 24 hours from the earlier of the latest stop's `stoppedAt` and the time the Hub last stored that stop. It clears after those 24 hours unless a newer stop has arrived, even without another Report and while the System is unpaired. A stop delivered later than that is stored but raises nothing. A current Service record or a failed check is not required, and forgetting a record does not end the note early.

The reason counts the latest run of stops, going back from the latest stop while each gap is at most 24 hours. It gives the first and last stop's `stoppedAt` in UTC, or the one time for a single stop. The latest result reads as stopped cleanly for `success`, failed with the result and exit status for any other result, or unknown when no check saw the Service stopped. An unknown exit status stays unknown, and a stop still under way says it is still stopped. Nonzero automatic restarts are counted across that run. Further stops and updates that end a stop change the reason without a Timeline transition. The note never steps up and is never delivered. The dashboard shows the Hub's reason in Can wait and offers advice to read the Service's log.

The Hub prunes ended stops whose `stopped_at` is older than 90 days. Ongoing stops stay until they end. Pruning stops leaves their Conditions and Timeline intact.

## Alert delivery

The Hub pushes Conditions at the alert level to one [ntfy](https://ntfy.sh) topic, as [ADR-0020](decisions/0020-the-hub-delivers-alerts-through-ntfy.md) decides. Notes and warnings are never pushed.

Delivery is configured in `[delivery]` in `hub.toml`, or the equivalent JSON `delivery` object. Without the section, delivery is off.

| Setting | Meaning |
| --- | --- |
| `url` | The ntfy server's address, `http` or `https`, such as `https://ntfy.sh`. |
| `topic` | The topic to publish to: 1 to 64 letters, digits, hyphens, or underscores. On a public server without a token, the topic name is the secret. |
| `token` | Optional. An ntfy access token, sent as a bearer token, for a reserved topic or a server that requires one. |
| `dashboard` | The dashboard's address, which each message links to. |

An unknown setting, a missing required setting, or an invalid value stops `serve` before it opens the database. The error names the setting and never its value. The Hub logs the server's host when it starts and never logs the topic or the token.

Every 30 seconds, the Hub compares the Conditions it stores with its record of deliveries. A delivery covers one identity (System, kind, and subject) for as long as it keeps reaching alert.

- **Push.** An identity at alert with no open delivery sends one high-priority message with the Hub's reason and how long the identity has been at alert. The delivery stays open across level changes and new occurrences, and sends nothing more while it is open.
- **Recovered.** Once the identity has stayed below alert for 10 minutes, cleared or open at a lower level, the delivery closes with one low-priority message. The message states the identity's current level, or that it cleared, and how many times the identity reached alert during the delivery. When the identity is back at alert by the time the message goes out, the message says so, and a new push follows it. Reaching alert again later opens a new delivery. The Hub reads when a delivery closed from the stored transitions, so a delivery that closed while sends were failing still closes, even when its identity has since returned to alert.
- **What is true now.** The Hub records a delivery only after ntfy accepts the message. A failed send records nothing, and the next pass tries again with what is stored then. An identity that reached alert and left it while ntfy was unreachable or the Hub was stopped sends nothing. One still at alert sends a single push. A delivery that was pushed earlier and closed meanwhile sends its recovered message, and an identity back at alert since then sends a new push after it. When delivery is first configured, the Conditions already open at alert send one push. Closed occurrences, such as backfilled history, never send.
- **Batching.** Recovered messages that come due in one pass go out as one message, then pushes as another. A message about one Condition opens that Condition's page on the dashboard. A message about several lists a line for each of the first 10, counts the rest, and opens the Fleet page. Long titles and lines are cut short, so a message stays within the 4,096 bytes ntfy publishes.

**Failing status.** The Hub stores when its current run of failed sends began, the first failure since the last successful send, in one row of the `delivery_status` table. A successful send clears it, and a pass that sends nothing leaves it as it was. The Hub records a delivered message before it clears the status, so a failed status write never causes a message to be sent twice or hides why a send failed. When `serve` starts without a `[delivery]` section, it clears the stored run, so turning delivery off leaves no stale status. Once the run is 10 minutes old, the dashboard's Fleet page shows "Alert delivery failing since" and the time, in the warning colour, below the verdict. This is a status of the Hub, not a Condition: it changes no verdict, count, or list.

**Testing the channel.** `heimdall-hub delivery test` reads `[delivery]` as `serve` does, including `--config`, sends one low-priority message titled "Heimdall test" that opens the dashboard, and prints the server's host. It takes the database like other commands, and a message that gets through clears the stored run of failed sends, so the dashboard stops saying delivery is failing before the next alert sends; a test that fails leaves the status as it was and never sets it. It exits 1 with the reason when `[delivery]` is missing or invalid, when ntfy cannot be reached, or when ntfy answers other than 2xx. It never prints the topic or the token.

**Silences.** `heimdall-hub silence <system> --for <duration>` holds delivery for one System until the duration passes, and replaces any silence the System held. A duration is days, hours, and minutes, such as `30m`, `2h`, `1d`, or `1h30m`, up to 365 days. `heimdall-hub silence <system> --clear` ends the silence, and `heimdall-hub silence` alone lists the active silences with their end and time left. Only a paired System can be silenced, and unpairing a System ends its silence. A silence is stored in the Hub's database, so it needs no restart and survives one. It never hides a Condition or changes a System's health, and the dashboard keeps showing every Condition. While a System is silenced, the Hub sends neither its pushes nor its recovered messages. Nothing else is recorded when a silence ends; the next pass reconciles as usual. A Condition still at alert then sends its push with how long it has been at alert. A delivery pushed before the silence that closed during it sends its recovered message. A delivery pushed before and still open sends nothing more. A Condition raised and cleared during the silence sends nothing. The dashboard shows an active silence, its end, and the time left on the System's Fleet card and on every tab of its page, and changes nothing else it shows.

When two Hubs share a database, as during an upgrade, one delivery pass runs at a time across them, so a message is never sent twice. Delivery covers paired Systems only. An unpaired System's open Conditions send nothing, and unpairing a System closes its open deliveries without a recovered message. The Hub publishes with one JSON request to the server's address and treats a redirect as a failed send.

## Reading the records back

The Collector sends its whole record set in a Report's `records` section when it starts, when a `record` or `forget` changes the set, and an hour after the Hub last answered a Report carrying the set. The section carries each record as the provisioner recorded it and the kind and name of each record the Collector could not read from its own state. A row whose kind or name the section cannot carry, which only a damaged state file holds, is left out, and the Collector logs a warning. A job's runs are not part of the set.

The Collector sends its jobs' latest runs in a Report's `runs` section when it starts, when a `record run` or `forget` changes them, and an hour after the Hub last answered a Report carrying them, so recording a run does not resend the record set. For each job that has reported a run, the section carries its latest run and its latest successful run, which may be the same run, or `null` when none of the runs the Collector keeps succeeded. A job whose latest run or latest success the Collector cannot read is listed by name as unreadable. Runs whose JSON is larger than 1 MiB are sent as their size alone.

The Collector sends the results of its checks in a Report's `checks` section when it starts, when they change, and an hour after the Hub last answered a Report carrying them. The section has parts, one for each kind of check, and the Collector builds them in loops of their own, so a part waits for no other. The files part has two fields, `fileRecords` and `files`. `fileRecords` lists each `files` record the Collector hashed, as the record's name (`record`) and its `digest`, which [Drift](#drift) defines. `files` lists only the recorded files in those records that are not matching. Each entry has the `record` that names the file, its `path`, its `state` (`drifted`, `missing`, or `unreadable`), and `since`, the Collector's clock as epoch milliseconds. A record whose row the Collector cannot read, or holds under a name other than its own or one the section cannot carry, is not listed in `fileRecords`, and the Collector logs a warning for the latter. An empty `files` beside a `fileRecords` that lists a record says every file in it matches, and is how the Hub learns that Drift has cleared. A section without a `files` part says the Collector has not finished a file pass yet, or is newer than this Hub, and judges no record.

The services part is `services`, which lists each check of each recorded Service: its `service` name, its `check` kind (`supervisor` or `health`), its `state` (`up`, `stopped`, `unhealthy`, `unknown`, or `unchecked`), its `detail`, and `since`, the Collector's clock as epoch milliseconds. [Service down](#service-down) defines them. An empty `services` says the Collector has no Service to check, and no `services` says nothing about any Service.

Every part is optional, and checks of other things join the section as further parts, so a section from a newer Collector that carries parts this Hub does not know, or only them, is still accepted, and the Hub drops what it does not know. The Collector sends no section until a loop has finished its first pass, and then sends the parts it has. Each part has a budget of 1 MiB of JSON. A part over it is sent as its size alone, in `overBudget` under the part's name (`files` or `services`), and the other parts are sent as they are, so a large files part never stops Services from being reported.

The Collector sends the [Service stops](#service-stops) it logged in a Report's `serviceStops` section while it holds any the Hub has not taken, oldest first and at most 1,000 to a Report. Each stop has the `service` name, `stoppedAt` and `startedAt` as epoch milliseconds on the System's clock, `startedAt` being `null` until the Service runs again or when its end is unknown, `ongoing`, `restarts`, `result`, a short word such as `exit-code` or `null`, and `exitStatus`, an integer or `null`. A Service and its `stoppedAt` name a stop, so a stop sent while `ongoing` is sent again with the same `stoppedAt` once it ends. Stops in one section have distinct (`service`, `stoppedAt`) keys. Each stop sent is the whole of what the Collector knows about it, `restarts` included, so the Hub replaces what it holds for that stop; the rule below for sections sent earlier does not apply to stops. A delivered Report settles the stops it carried, and the Collector drops those that ended; a stop that changes later is sent again. A failed delivery keeps them, and a refused one keeps them and holds them back for an hour. A Hub that predates the section drops it and still takes the Report, so the Hub is upgraded before its Collectors.

Every Report also carries the System's IANA time zone, such as `America/New_York`, in which its jobs' schedules are read. The Collector reads it on each Report from the zone `/etc/localtime` names, which is where systemd and macOS record the zone their schedulers follow, so a change of zone shows in the next Report. A Report carries no zone when `/etc/localtime` names none.

If the Hub refuses a Report carrying the set, the runs, the checks, or the Service stops, the Collector sends the same samples again without them, so none ever costs Vitals, and offers each again an hour later. A Report that would be too large for the Hub with them is sent without them, and they ride a later, smaller Report.

The Hub replaces the System's mirror with each set, so a forgotten record leaves the mirror, and replaces the System's latest runs and latest checks with each runs and checks section in the same way. It ignores a section sent earlier than the one it holds, unless the held one claims a time later than the Hub's own clock. A Report without a section leaves what the Hub holds for it unchanged, and one without a time zone keeps the zone the Hub holds.

The Hub drops a field it does not know from a mirrored record or run. It counts a record of a kind or shape it does not know as unreadable, since the record still exists on the System, and likewise a job whose latest runs it cannot read. A set whose JSON is larger than 8 MiB is sent as its size alone, and the Hub then holds no records for that System until a smaller set arrives; runs over budget likewise leave it no jobs, a files part over budget no files, and a services part over budget no Service checks. The Hub counts a file state it does not know as unreadable and a Service state it does not know as unknown, and drops a Service check of a kind it does not know. It ignores a time zone it does not accept and keeps the one it holds. The shapes are in `packages/schema/src/records-section.ts`, `packages/schema/src/runs-section.ts`, and `packages/schema/src/checks-section.ts`.

The dashboard serves the records read at its own address: `GET /api/v1/records` returns every paired System's records, with the same trust as the dashboard's pages. The Hub does not serve it. The answer lists each paired System that has sent a Report, sorted by name as the dashboard sorts them, in one of three forms:

Pairing the System again lists it without the parameter once the new code is redeemed; until then it stays unpaired. `records` is `null` until a Report carries the System's set, `runs` until a Report carries its runs, `checks` until a Report carries its checks, and `timeZone` until a Report names one, which a Collector older than each never sends. A checks entry with no `files` and no `fileRecords` says no file pass has reached the Hub yet, or that the part was sent over budget, which is not the same as an empty `files`: nothing has been judged. Its `fileRecords` lists each `files` record the Collector hashed with the [digest](#drift) it read, so a provisioner can tell checks that judged an older version of a record from the record the Hub mirrors now; a record missing from it, or listed with another digest, was not judged as mirrored. Its `services` lists each check of each Service with its state, detail, and `since`, so a provisioner can see which Services the Collector found stopped, unknown, or unchecked. A part sent over budget is left out and named in `overBudget` with its size, and `services`, `files`, and `fileRecords` are also left out when the Collector sent no such part, which is not the same as an empty list. Records are sorted by kind, then name, jobs' runs by job, checked records by record, checked files by record, then path, and Service checks by service, then check, each by code unit. Times are UTC in ISO 8601, including each file's and each Service check's `since`.

The dashboard serves Service stops at `GET /api/v1/service-stops[?system=<name>][&service=<name>][&since=<ISO 8601 time>][&unpaired=include]`, apart from `GET /api/v1/records` ([ADR-0011](decisions/0011-collectors-hold-what-provisioners-record.md)). The answer is 200 with the stops the Hub holds:

```json
{"stops": [
  {"system": "web-1", "paired": true, "service": "webapp",

   "ongoing": false, "restarts": 2, "result": "exit-code", "exitStatus": 1,
   "sentAt": "2026-10-24T07:42:00.000Z", "receivedAt": "2026-10-24T07:42:00.410Z"}

```

`system` and `service` are optional exact-match filters. `since` keeps stops whose `stoppedAt` is at or after that time, given as a date, `T`, and a time to the minute or second with optional fractions, then `Z` or an offset, such as `2026-10-24T07:40:05Z`; its date and hour must exist, so `2026-02-30` and `24:00` are refused. With no filters, the read returns every stop of paired Systems that the Hub holds: those of its 90 days, and any stop still under way, however old, since the Hub keeps that until it ends. `unpaired=include` adds unpaired Systems' stops, each with `paired: false`. Every `unpaired` value must be exactly `include`, and repeating it is allowed. A repeated or empty `system`, `service`, or `since`, a `since` of another form, or another `unpaired` value answers 400 with a short plain-text reason. Unknown parameters are ignored.

Stops sort by System, then Service, each by code unit, then by `stoppedAt` newest first. `startedAt`, `result`, and `exitStatus` can be null. Times are UTC ISO 8601 with milliseconds. `stoppedAt`, `startedAt`, and `sentAt` are on the System's clock, and `receivedAt` is on the Hub's. A database that cannot be opened or read answers 503. Other methods answer 405, with HEAD answered from GET as for the records read.

## Agent Session transcripts

A System captures transcripts only from the sources its Collector configuration lists ([ADR-0013](decisions/0013-transcripts-upload-as-acknowledged-chunks-into-postgresql.md)). Capture is off until a source is listed:

```toml
[[sessions.sources]]
harness = "claude-code"            # its standard directory

[[sessions.sources]]
harness = "claude-code"
dir = "~/.claude-work"             # a second profile
name = "claude-work"
```

Each source names a Harness, and optionally a directory and a name, which default to the Harness's standard location and its name. A directory is absolute or starts with `~/`. Two sources may not share a name or a directory, even through a symbolic link, and the Collector refuses to start with such a configuration or with a Harness it does not know. A source whose directory does not exist is skipped, so one configuration can list every source a fleet uses. The Collector reads each directory as its own account and reports each source as capturing, absent, or unreadable. Adding a source uploads the history already in it.

| Harness | Standard directory | Session tree |
| --- | --- | --- |
| `claude-code` | `~/.claude` | `projects/` |
| `codex` | `~/.codex` | `sessions/` |

The Collector uploads every file of a source's session tree to the Hub as it grows, separately from Reports, as gzipped chunks the Hub acknowledges by offset. It keeps content the Hub has not acknowledged in a spool, so a Harness pruning its files loses nothing. It reads the trees every 60 seconds, reads only regular files, follows no symbolic link inside a tree, and skips a file whose name is not UTF-8, which has no path the Hub accepts. A JSONL file's chunks end on line boundaries; a last line without a newline, and a whole file that is not JSONL, upload once the file is unchanged across two scans. The Hub stores transcripts as written and keeps them until they are deleted on purpose.

### Upload protocol

A Collector uploads with its System's token as a bearer token, like a Report. The limits and request shapes are in `packages/schema/src/transcripts.ts`.

1. **Open a generation** for each file the Collector has not uploaded before, and whenever a file it has uploaded shrinks, is replaced, or stops matching what it uploaded: `POST /api/v1/transcripts/generations` with `{"source": "claude-code", "path": "projects/my-project/0b1c.jsonl"}`. The path is relative to the source's directory, as the directory lists it, with `/` between segments, and is valid UTF-8 of at most 4096 bytes; a file whose name cannot be written so has no path the Hub accepts. The Hub answers `201` with `{"generation": 42, "held": 0}`.
2. **Send each chunk** of the file in order: `POST /api/v1/transcripts/generations/42/chunks` with the gzipped chunk as the body, as one gzip member or several concatenated, and its offset, counted in bytes of the file before compression, in the `Heimdall-Offset` header. A chunk carries at most 1 MiB of the file and its body at most 2 MiB. The Hub stores the chunk as uploaded and answers `{"held": <bytes of the file it holds>}` in the same transaction.

| Answer | Meaning | The Collector |
| --- | --- | --- |
| `200 {"held": n}` | The chunk is stored, or the Hub held it already. | Removes what the Hub holds from its spool. |
| `409 {"held": n}` | The offset is not where the Hub's content ends. | Resumes from `n` when its spool continues there. Otherwise, as when the Hub holds more than the file has, the file starts over in a new generation. |
| `410` to an open | Every generation at the path was deleted on purpose. | Stops uploading the path and drops its spooled content. |
| `410` to a chunk | The generation was deleted on purpose. A newer generation at the same path may survive. | Drops the generation's spooled content. If the file still grows into it, opens a new generation at the path, and stops the path when that open is refused. |
| `404` | The System opened no such generation. | Opens a new generation when the spool still holds the file from its first byte; otherwise drops the spooled content, and the file starts over in a new generation at the next scan. |
| `401`, `403` | No token, or a token no System holds. | Keeps its spool and retries. |
| `413`, `422` | The chunk body is over the cap, is not gzip, or unpacks past the chunk limit, or the request is malformed, such as an open with an invalid path or a body over 32 KiB. | Keeps that file's spool and retries after backing off, while other files still upload; it is a Collector bug. |

Every upload counts toward the System's Last seen, and no refusal raises a Condition. Every Report carries a `transcripts` section: each source's name, Harness, and status, and the spool's size and the time of its oldest content. A Collector that captures nothing sends no sources and, once what a removed source left is uploaded, an empty spool. The Hub keeps each System's section from the latest Report it was sent in; a Report from a Collector older than this section leaves it unchanged.

`heimdall-hub transcripts delete` deletes whole generations that match every filter given: `--system`, `--source`, and `--before <date>`, which compares a generation's last upload with the start of that day in UTC. At least one filter is required, and `--dry-run` reports what would be deleted. Once every generation at a path is deleted, the Hub refuses new generations there. The [Session insight](#session-insight) derived from deleted generations goes with them.

`heimdall-hub transcripts show` prints transcript lines to stdout as the Hub holds them. It runs on the Hub's System with the Hub's own database access, the only way the raw lines leave the database. It takes a Session, a request, or a locator:

- `--system`, `--source`, and `--session <id>` print the Session's main conversation. `--agent <id>` prints one of its subagents instead, by an `agent_id` from `insight.subagents`. It reads the newest generation at the transcript's path that is not deleted, which is the file as it stands.
- `--system`, `--source`, and `--request <id>` print every line of a request, by a `request_id` from `insight.requests`. A request can span several lines: Claude Code writes one line per content block of a response, thinking, text, and each tool use, all under its `message.id`. The Harness's parser names the request each line belongs to. The command reads every generation that holds the request, the one its locator names first, and prints a line that several generations hold once.
- `--generation <id>` prints that whole generation, and with `--offset <bytes>` only the line that starts at that offset, through its newline. These are the `generation` and `byte_offset` of a locator in `insight.requests` or `insight.tool_calls`. A tool call's locator names the line that holds the call. A request's names the line its usage was read from, which for Claude Code is the response's last line with a stop reason, and holds only that line's content block; `--request` prints the rest. `--system`, `--source`, and `--path` are optional with a locator, and when given, the generation must match them.

An unknown Session, subagent, request, or generation, a deleted generation, and an offset that does not start a line the generation holds each end the command with a message on stderr and exit code 1. Piped, the output is the bytes as stored. On a terminal, every control character is escaped, so no line can drive the terminal. A migration the command applies is reported on stderr, so stdout holds only transcript lines.

The Collector observes Harness processes beside transcripts; see [Harness processes](#harness-processes).

## Installed Harnesses

The Collector reports which Harnesses are installed on its System and at what version, in a Report's `harnesses` section. It finds them by reading directories and package metadata under the account's home directory and the well-known system locations, never by running a Harness: it starts no `claude` or `codex`, so a Harness's own update or telemetry check never runs because of Heimdall. Tool-manager install directories and package metadata are observations, not a provisioner's records.

The section is `{"installs": [{"harness": "claude-code", "location": "mise", "version": "2.1.296"}]}`. Each entry is one install: the `harness`, the `location` kind it was found in, and its `version`. No path is sent. A Harness that is not installed has no entry, and a System with none sends an empty list, which is not the same as a Report without the section. When the Collector finds an install and cannot read its version, in any location kind, the entry's version is `unknown`: a tool directory that is there (its parent lists it) and cannot be listed, a package directory that is there (its parent lists it) and whose `package.json` is missing, too large (over 64 KiB), not a regular file, or without a usable version, and an install that has no release version, such as a mise `ref-<name>` install or a Homebrew `HEAD-<sha>` keg. A System with two installs of one Harness lists both, one entry for each location and version found, in order of Harness, then location, then version; the same location and version found by two paths counts once. Each Harness keeps its newest 32 entries by version, so a Harness with many versions never crowds out another.

| Location kind | Where the Collector looks | The version comes from |
| --- | --- | --- |
| `mise` | `installs/<tool>/` under mise's data directory (`$MISE_DATA_DIR`, else `$XDG_DATA_HOME/mise`, else `~/.local/share/mise`), for the tool names `claude` and `npm-anthropic-ai-claude-code`, or `codex` and `npm-openai-codex` | The name of each directory that is a version. Names that are not a full version, such as the symbolic links `latest` and `2.1`, are skipped, but a link named for a full version counts, as `mise link` makes one. |
| `native` | `claude/versions/` under the data directory (`$XDG_DATA_HOME`, else `~/.local/share`), where Claude Code's native installer keeps one file per version | The name of each entry that is a version. |
| `npm` | `node_modules/@anthropic-ai/claude-code` or `node_modules/@openai/codex` under `~/.npm-global/lib`, `~/.local/lib`, `~/.bun/install/global`, and the system prefixes: `/usr/lib` and `/usr/local/lib` on Linux, `/opt/homebrew/lib` and `/usr/local/lib` on macOS; for Claude Code also `~/.claude/local/node_modules` | The `version` in the package's `package.json`. |
| `homebrew` | `Cellar/<name>/` and `Caskroom/<name>/` under the Homebrew prefix, for `claude-code` or `codex`: `/opt/homebrew` and `/usr/local` on macOS, `/home/linuxbrew/.linuxbrew` and `~/.linuxbrew` on Linux | The name of each directory that is a version. |

A directory name counts as a version when it reads as `major.minor.patch`, each number of at most 8 digits, with an optional `-` or `+` suffix, and the whole is at most 64 characters; a longer or stranger name is not a version. A Homebrew keg name may end in a revision such as `_1`; the reported version leaves it off. A directory the Collector cannot list costs only the installs under it, and it reports an unknown install only when its parent directory can be listed and holds it; when the parent cannot be listed either, nothing is reported for that place. Other places, such as Node version managers other than mise, are not read; a Harness installed only there is not reported.

The Collector looks for installs when it starts and every 10 minutes, and sends the section when it starts, when it changes, and an hour after the Hub last answered a Report carrying it. If the Hub refuses a Report carrying it, the samples are sent again without it, as for the other sections. The Hub keeps each System's latest list, ignores one sent earlier than the one it holds unless the held one claims a time later than the Hub's own clock, leaves it unchanged for a Report without the section, and shows it beside each System on the dashboard.

## Harness processes

The Collector watches the process table for Harness root processes and reports them in a Report's `harnessProcesses` section, so the Hub can set a Session's transcript beside the CPU and memory its Harness used. From the process table it reads only an executable's name, its parent, start, CPU time, resident memory, and working directory. It never reads command-line arguments or environment variables ([ADR-0002](decisions/0002-collector-observes-processes-never-content.md)).

**What counts.** A process is a Harness process when its name is exactly one of the Harness's names: `claude` for Claude Code and `codex` for Codex. On Linux the name is the kernel's command name, and the Collector confirms it with the process's executable: the executable's file name must be the same name, or the executable must sit in the Harness's native install directory (`claude/versions` under a data directory), where Claude Code's native installer names each executable by its version. A process whose executable is something else, such as `node`, is named by its executable. On macOS the name is the accounting name `ps` prints as `ucomm`, the file name of the executable the process runs, cut to 16 bytes. For a process whose accounting name is a Harness's or reads as a version, the Collector asks the kernel for the executable's path and applies the same rule as on Linux, so a native Claude Code, whose accounting name is its version, counts as Claude Code when its executable sits in `claude/versions`, and a version-named executable anywhere else does not. Identity is by name, so any executable named `claude` counts as Claude Code. A Harness that runs as a script under another runtime shows as that runtime, is not matched, and cannot be told apart without its arguments. A **root** is a Harness process whose parent is not a process of the same Harness, so a helper Claude Code starts under itself is part of its root's tree, while a Claude Code that an SDK host, a shell, or another Harness starts is a root of its own. Codex runs its subagents as threads of one process, so they get no process of their own and are not told apart here.

**What a row says.** Each process in the section has its `harness`, `pid`, `startedAt` (to the second), `cwd` (null when unreadable, such as another user's process; a directory removed while the process runs is reported by the path it had), `repository`, `cpuMicros`, `rssBytes`, `peakRssBytes`, `lastSeenAt`, and, once gone, `endedAt`.

- `repository` is the absolute path of the repository `cwd` belongs to, whose last folder names the project, and null when it belongs to none or the Collector could not tell. A Collector older than [ADR-0019](decisions/0019-a-sessions-project-is-the-git-repository-of-its-working-directory.md) omits it. The Collector looks a directory up when a process is first seen in it and again only when the process's `cwd` changes, walking up from `cwd` to the first `.git` entry and reading only git's pointer files, never running git and never reading anything else in the repository. A `.git` directory makes its parent the repository. A `.git` file holds `gitdir: <path>` on its first line: when that git directory has a `commondir` file, which every linked worktree's has, the repository follows from the common directory it names: one whose name starts with a dot, such as `.git` or a `.bare` kept inside a project folder, names its parent; one whose name ends in `.git` names itself without the suffix; any other names itself. A git directory without a `commondir` file, such as a submodule's or the `.bare` a project folder's own `.git` file points to, makes the working directory its own repository. A `.git` entry that is there but unusable, or a `commondir` file that is empty or cannot be read, makes `repository` null without looking further up. ADR-0019 lists the layouts this names wrongly.
- `cpuMicros` is the user and system CPU time the process and its descendants have used, as read at `lastSeenAt`. On Linux it includes children already reaped, so a build that has finished still counts; on macOS it is the live processes' time. CPU used over a span is the difference of two readings.
- Each CPU second counts once. A root's totals leave out the trees of other roots under it, which count in their own root. On Linux, when a nested root ends and a process in the enclosing root's tree waits for it, its time moves into that tree's reaped children's time (`cutime` and `cstime`), so the Collector subtracts the nested root's last reading from the enclosing root's from then on. It subtracts no more than the tree's reaped children's time grew on the tick that found the nested root gone and the tick after, so time that arrives a tick late still counts once, and a nested root that something outside the tree waited for, such as init after it was orphaned, takes nothing from its former enclosing root. CPU the nested root used after its last reading still counts in the enclosing root. The kernel sums reaped time without saying which child it came from, so this is an approximation at its edges: time reaped two or more ticks late counts twice, and an unrelated child reaped within those two ticks, while an orphaned nested root takes nothing, is subtracted in its place. On macOS no reaped time is counted, so nothing is subtracted. A process's reported `cpuMicros` never falls: a reading below the last one reported, as when a descendant leaves the tree, reports the last one again.
- `rssBytes` is the sum of the tree's resident memory at `lastSeenAt`, which counts shared pages once per process. `peakRssBytes` is the highest of those the Collector saw.
- One Harness process can run several Sessions in turn, and one Session can run in several processes in turn. The Hub links each stretch of a Session to the process that ran it by Harness, System, working directory, and time, and only when the match is unambiguous, as [Linking Harness processes to Sessions](#linking-harness-processes-to-sessions) describes.

**How it is read.** The Collector shares one table pass per 15-second Vitals interval between Harness tracking and hot-process observations.
On Linux it reads each process's `/proc/<pid>/stat`, at most 64 at once.
It reads `exe` links for Harness candidates and the hottest processes, and `cwd` links for Harness roots.
On macOS it runs `ps -axww -o pid=,ppid=,rss=,etime=,time=,ucomm=` once.
Through libproc in libSystem and `bun:ffi`, `proc_pidpath` resolves executable paths for Harness candidates and the hottest processes.
`proc_pidinfo` reads each root's working directory and exact BSD start where permitted.
When it first sees a root, and again when the root's working directory changes, on either platform, the Collector checks for a `.git` entry in it and each folder above it until it finds one, and reads the first 4 KiB of that entry when it is a regular file, and of the `commondir` file in the git directory it points to; it opens each without blocking and reads it only when the open file is regular, and an entry it cannot examine stops the walk as an unusable one.
It also reads every process's cross-user lifetime identifier for hot-process observations, which `ps` does not supply.
No column or call reads a process's arguments or environment.

**Identity.** A process is its System, Harness, pid, and start. Within one Collector run, a pid read again is the same process when the kernel's record of its start is the same: the start in clock ticks since boot on Linux, and the start time the kernel recorded on macOS. A wall-clock step moves neither, and a process's `startedAt` is the one the Collector computed when it first saw the process, so a step never splits a running process. On macOS, when the kernel will not give a process's start, the start is the time `etime` ago, to the second, and a pid seen again with a start more than 5 seconds apart is a new process. The Hub matches a section to its rows by Harness, pid, and a start within the same 5 seconds; when a pid was reused within them, each process takes the row whose start is closest, and each row is taken by one process. Across a Collector restart, a Linux start is computed again from the boot time, which moves with every wall-clock step since boot; a restart after a step of more than 5 seconds splits each running process into the row the Hub closes as missed and a new one.

**Ends.** The section lists every root running now, with no `endedAt`, and every root that ended and the Hub has not acknowledged, with an `endedAt` that is the time of the tick that found it gone, so the true end falls up to one interval earlier. The Collector keeps ended roots until the Hub answers a Report carrying them, so an outage loses no end. A section lists at most 512 processes, running and ended together: the running ones first, then as many ended ones as fit, the oldest dropped first. If the Hub refuses a Report carrying the section, the ended roots it carried count as answered and are dropped too, since a refused Report counts as seen ([ADR-0005](decisions/0005-rejected-reports-count-as-seen-conditions-keep-a-timeline.md)). A dropped end reaches the Hub as a missed one, as below, when the Hub held the process as running; a process that started and ended between Reports the Hub stored never reaches it. When the Collector was not running to see a process end, the Hub closes it too: a process the Hub holds as running that a later section no longer lists gets the last time the Collector saw it as its end, and is marked as an end the Collector missed, since the real end is later than that. A process that is running has no end in the Hub either.

**What the Hub keeps.** The Hub keeps one row per process, with its working directory, repository, start, end, peak memory, and last sighting, and keeps the rows. A section that carries a working directory sets the repository with it, null included, unless it comes from a Collector that does not send `repository`. A row changes only for a section sent no earlier than the one that last touched it, unless the row claims a time later than the Hub's own clock. Each reading a section carries, a process's `cpuMicros` and `rssBytes` at its `lastSeenAt`, is a sample on the Vitals time axis, stored once however often it is resent, and rolled up into 5-minute buckets as it arrives. Samples and their rollups follow Vitals retention: samples for 14 days and rollups for a year ([ADR-0008](decisions/0008-vitals-roll-up-as-they-arrive-serve-prunes.md)). A Report without the section leaves the rows as they are.

## Session insight

The Hub derives Session insight from the transcripts it holds: each Session, each of its subagents, each request, and each tool call. The facts are a projection of the archive that the Hub can always rebuild from it ([ADR-0014](decisions/0014-session-insight-is-a-rebuildable-projection-read-through-insight-views.md)). The Hub parses transcripts after it stores them, never as they arrive. Every reader reads the facts through the views in the `insight` schema, described [below](#the-insight-views). The views also compute [cost](#cost) when read.

### How the Hub parses

Each Harness has a parser with a version number. Claude Code and Codex have parsers. A source runs the Harness the latest Report sent for its System names for it. The Hub remembers that Harness after the source leaves the Collector's configuration, so a removed source's transcripts are still parsed. A source no Report has named waits until one does. Transcripts the Hub held before it remembered Harnesses, from a source that no held set names, run the Harness the source is named after, which is the default name.

`serve` parses every 15 seconds. Each run reads up to a budget of 64 MiB of transcript content, and every chunk it fetches counts in full, including a chunk it fetches again and a read that fails. A read asks for no more than is left of the budget, unless no whole line fits in that: then the run reads again from the same byte, up to 16 MiB and a byte, to finish the line that crosses the budget. A read fetches whole chunks, so up to 1 MiB more than it asks for at each end, and a run fetches at most 84 MiB. It reads each generation from where its parser last stopped, in batches of at most 16 MiB and a byte, enough for a line at the cap and its newline, joining the generation's chunks in offset order, oldest upload first. A read fetches the chunks two at a time and unpacks them one at a time, so it holds no more than its batch, two packed chunks, and one unpacked. A line without its newline waits for the rest unless it is the last line the generation holds and reads as JSON, so a line the Collector split across chunks is parsed once it is whole. A batch stops after the line at which it holds 100,000 requests and tool calls, and the next batch starts after that line; the database stores a batch's facts in statements of at most 5,000 rows each. A batch's facts and the generation's progress commit together, and the progress moves only from where the batch was read, so a run that fails, a Hub that restarts, or a delete during a run loses nothing: the next run resumes from the progress as it stands. When the Hub keeps up, Session insight trails an upload by about 15 seconds, and a Session by about a minute more, since a Collector uploads every 60 seconds. A backlog or a rebuild parses up to 64 MiB a run, so it trails further until it catches up.

The parser holds every line to bounds, so one bad line never stops the rest:

- A line longer than 16 MiB is unreadable. The Hub skips it 16 MiB at a time as it reads, so it never holds the line whole.
- NUL and unpaired surrogates in text become U+FFFD.
- An id or a name is at most 255 characters, and other text at most 4096. A working directory and a branch are text, kept as written.
- A token count is a whole number from 0 to 1,000,000,000.
- A time is within the years 1 to 9999, and a response must have one.

A line that breaks a bound, or is not JSON, yields nothing and is counted unreadable.

A field that names or identifies something holds only a value shaped as one, so no prose a line carries there reaches the views:

- A model, a tool, an MCP server, an agent type, a workflow phase, or a stop reason is a letter or digit followed by letters, digits, and `:_./@+-`.
- An id, such as a response's, a tool call's, a line's `uuid`, a subagent's spawning tool call, or its parent agent, is a letter or digit followed by letters, digits, and `_.:-`. So are the Session id, agent id, and workflow run a file's path names. A file whose path names any of them otherwise is misnamed: it yields no Session or subagent, and `insight.parse_status` counts it.
- A Harness version is a digit followed by letters, digits, and `.+-`.
- A command or a skill is shaped as the [Claude Code](#claude-code) section describes.

A value not shaped as its field requires is left out. When a fact needs it, as a request needs its id and model, a tool call its id, name, and MCP server, and a command its name and its line's `uuid`, the fact is left out too and the line is counted unreadable. Otherwise the field is null, and the line is read.

A generation that cannot be read, through a gap between its chunks or a chunk that does not unpack to its stored length, is recorded failed for the parser's version, and so is one whose facts the database refuses. Any other error parsing a generation, such as a parser error or a statement that outlasts its timeout, fails that attempt, and the run goes on to the next generation; a generation whose attempts fail three runs in a row is recorded failed too. A batch that stores starts the count again. `serve` logs each generation recorded failed. A failed generation no longer counts as pending, so the rest of the archive proceeds and the views can switch without it. The parser's next version tries it again. An error that is no generation's fault counts against none: a lost or refused connection, or a server out of resources, shutting down, or restarting, which are SQLSTATE classes 08 and 53 and the states 57P01 to 57P03, and Bun's own errors for a connection it could not open, lost, or found the server had ended, including a socket it could not open at all, which carries no code. The run stops, `serve` logs it, and the next run tries again.

Every fact carries its Harness and the parser version that wrote it, and the `insight` views show only each Harness's current version. A Harness's first version becomes current once no generation is pending for it. A Hub whose parser has a later version than the current one rebuilds: it writes that version's facts beside the current ones, and runs only its own parser, so the current set stays as it was while the views keep showing it. The views switch to the new version in one statement once it has read every generation at least as far as the current version had, unless it failed there. An upload that lands during the rebuild, which the current version has not read either, does not hold the switch back. `serve` logs the switch. That run and the ones after it delete the earlier version's facts, at most 10,000 rows of each table a run. A restart during a rebuild resumes it. Until a Harness's first version is current, the views show none of its Sessions.

Versions only move forward. A Hub whose parser is older than its Harness's current version, as when two Hubs share a database during an upgrade, leaves that Harness alone and logs why. No Hub switches a Harness back to an earlier version. A Hub deletes only facts of versions earlier than both the current version, which each delete reads as it runs, and its own. A version earlier than the current one never becomes current again, so no Hub deletes the current version's facts or a newer Hub's rebuild, and a Hub that falls behind during a run deletes none of a version later than its own.

A request counts once within a System's source, however many generations or files hold it, keyed by the Harness's own id for it, and so does a tool call. Deleting generations with `heimdall-hub transcripts delete` deletes, in the same transaction, the facts of every Session the generations touched, and resets that Session's other generations so the next runs parse them again. The Session leaves the views until its current version has parsed it again from the generations that still hold it, so it reappears whole and never half-built. A request or a tool call that another Session's generation still holds is derived again from that generation, and that Session stays shown. A live Session that only grows stays shown, its new facts appearing as they are parsed. The cleanup of an earlier version's facts takes no lock, so it can deadlock with a delete, and PostgreSQL aborts one of them. An aborted cleanup loses nothing and a later run repeats it; an aborted delete tries its transaction again, up to three tries with a short backoff, and fails with the deadlock after the third, having deleted nothing. A delete waits for any batch being stored to commit, and no batch is stored while a delete runs: a run that finds one under way leaves the rest to the next run. So a batch either commits before the delete reads the facts, or finds its generation deleted or its progress reset, and nothing derived outlives its transcript. A Session touched during a rebuild stays hidden until the rebuild's version is current and has parsed it again, since only the new parser runs.

### Claude Code

The parser reads a source's `projects/` tree:

- **A Session** is a main conversation, `projects/<encoded cwd>/<session id>.jsonl`. A resumed Session appends to its file under the same id, so it stays one Session, and the Harness version at its first and last line can differ. `/clear` starts a new Session in a new file. A Session that keeps its file and id when it is compacted stays one Session; no compaction appeared in the transcripts the parser was checked against.
- **A subagent** is `<session id>/subagents/agent-<agent id>.jsonl`, and a workflow agent `<session id>/subagents/workflows/<run>/agent-<agent id>.jsonl`. The `.meta.json` beside each names its agent type and spawn depth, and either the tool call that spawned it, which the parent conversation, the main conversation or another subagent, made, or the phase of the workflow run that started it. A workflow's `journal.jsonl`, tool outputs in `tool-results/`, and memory files hold no facts and are not read.
- **A request** is one API response. Claude Code writes one line per content block and repeats the response's usage on each, so the parser keeps one line per `message.id`: the last line with a stop reason, or, for a response that was interrupted and has none, the last line. A `<synthetic>` message, which Claude Code writes itself, is not a request. A request names the model the API answered with, such as `claude-haiku-4-5-20251001`, which can differ from the alias Claude Code's own cost tally uses.
- **Tokens** are as Claude Code recorded them. Reasoning tokens are within output tokens, and cache write tokens are split into 5-minute and 1-hour writes. Context fill is input, cache read, and cache write tokens together.
- **A tool call** is a `tool_use` block, and the first line that holds a call keeps it. An MCP tool, `mcp__<server>__<tool>`, names its server, and the `Skill` tool names its skill. A slash command a person typed, from `<command-name>` in a user line, is a tool call of kind `command` that names the command and no skill, since a built-in command such as `/doctor` is none. A request also names the skill Claude Code attributed it to. A command or skill name is a letter or digit followed by at most 63 letters, digits, and `:_./-`, after an optional `/`. A command named anything else, such as prose a prompt wrapped in the tag, is left out and the line counted unreadable, and a skill named anything else is null: the views carry no content. Listings of the skills available invoke none.
- **A command's id** is its line's `uuid` for the line's first command, and `<uuid>#1`, `<uuid>#2`, and so on for the rest, or, where that would pass 255 characters, the `uuid`'s SHA-256 in hex followed by `#1` and so on. The first line with a command under a `uuid` owns every command under it, so a later line with the same `uuid`, as when Claude Code writes a line again, adds none, however many commands it carries.
- **Times** are not in order within a file, so a Session or subagent spans its earliest and latest line, with the working directory, branch, and Harness version of each.

Totals from transcripts match Claude Code's own running tally, the `cost-state` lines in a main transcript, with three known gaps. Claude Code counts side requests, such as naming the Session, that it never writes to a transcript. An interrupted response is recorded with the usage of its last line, which can be lower than what the response used. And the tally can miss an interrupted subagent response that the transcript records, which the totals count.

### Codex

The versioned parser reads a Codex source's `sessions/**/rollout-*.jsonl` files. Its fixtures pin the format measured in Codex 0.154.0–0.162.1. Codex's first parser version waits for a source mapped to Codex before becoming current, avoiding an announcement for an unused Harness. Claude Code's first version still becomes current when no generation is pending.

- **Identity** comes from `session_meta.payload.id` in the file's first record, with `cwd` and `cli_version` from that header. Git is a start snapshot and may be absent. A copied parent's header never replaces the file's identity. The first record is the header attempt: anything other than a valid `session_meta` invalidates the file's identity, so it has no owner and yields no facts. A run started as a separate program, including `codex exec`, is a Session of its own.
- **A subagent** carries `session_meta.payload.parent_thread_id`, its immediate parent thread. The Hub links nested subagents to the root Session and exposes their immediate parent in `insight.subagents.parent_agent_id`. Upload order does not change the resulting hierarchy. A missing parent's transcript leaves a Session with a null main path, as with Claude Code.
- **Fork replay** is identified only by explicit rollout `ordinal < subagent_history_start_ordinal`. The parser keeps the child's own header and drops every inherited record, including copied headers and the 3–4 replayed lines per measured file with no parent match. Those unmatched lines are inherited context, not new child work. Timestamps and matching against the parent's file do not decide ownership. A fork with a cutoff but no ordinal drops the affected record and counts it unreadable. A legacy fork with `forked_from_id` but no cutoff is counted unreadable and yields no facts: its replay boundary cannot be recovered reliably. Other legacy files with no fork need no ordinal.
- **A request** is `token_usage_record.payload.usage`, keyed by its unique `response_id`. The parser never sums `total_*`, `thread_*`, or `turn_*` fields or counts requests from `token_count` events. Repeated token-count events, including the measured 195 of 4,153 events that repeat the previous total, add no usage. Requests use the model in `turn_context.payload.model` for their own `turn_id`, even across a model switch. A request conflict cannot move a Codex response to another conversation. Usage before any turn context, or for an unknown turn id, is retained with model `unknown`, a reserved unpriced sentinel. Every Codex request's `stop_reason` is `completed`. Interrupted responses have no usage record and are absent from requests and totals, rather than estimated from token-count events.
- **Tokens** keep the shared projection's meaning. Codex's `cached_input_tokens` are within `input_tokens`, so the projection separates cache reads from uncached input. Reasoning is within output. A request whose cache reads plus writes exceed input, or whose reasoning exceeds output, is dropped and counted unreadable, including when its model is unknown. Cache writes are kept separately and were zero in every measured request; Codex records no duration split. A main fixture's per-request totals reconcile with its final cumulative usage. A compacted Session's do not: the request that compacts it has a usage record, which the totals count, and Codex's cumulative usage leaves it out. A fork's cumulative usage also contains the inherited baseline, which must be removed before reconciling its own requests.
- **Context window** is stored per request in `projected_requests.context_window`, and `insight.requests.context_window` reads it before the price table's (see [Cost](#cost)). It comes from the request's `turn_started.model_context_window`; `token_count.info.model_context_window` can fill an unknown window for later requests in the current turn. A missing window stays null; a later turn-start event without a window preserves the window already learned. Token-count events usually follow their usage record, so they are not assumed to describe the next turn's model. Continuation state retains the header, replay boundary, and the latest 1,000 turn identities, models, and windows across batches. The projection stores the owner agent id separately in `parse_progress.agent_id`; continuation state is opaque to the projection.
- **Tools** are completed `CommandExecution`, `McpToolCall`, `FileChange`, and `CollabAgentToolCall` items in `event_msg/item_completed`. The enclosing `exec` custom call adds none. MCP items expose their server and tool, and collaboration items expose their tool. Commands and file changes use their item type as the name. Item ids are hashed with the thread id to count a local item once without collisions between threads. Completed items identify a turn rather than an API response, so their `request_id` stays null.
- **Skills** have no recorded invocation event. Reads of `skills/<name>/SKILL.md` and user `<skill><name>…</name>…</skill>` messages infer a skill. `insight.tool_calls.skill_inferred`, appended at the end, is true for these facts and false for Claude Code's recorded invocations. Every inferred skill has its own row of kind `tool`, name `Skill`, and `skill_inferred = true`. CommandExecution rows carry no skill annotation. Counts of completed tool items exclude inferred skill rows. Skill messages count once by thread, timestamp, and shaped skill name. Listings of available skills infer none. Message text, commands, file changes, and tool output never reach a view.

**Parent cumulative totals exclude later subagent usage.** The pinned [0.154.0 Session state](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/state/session.rs) and [0.162.1 Session state](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/core/src/state/session.rs) accumulate only that thread's responses. The [Session implementation](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/core/src/session/mod.rs) records usage with its own thread id, seeds a fork from inherited history, and sends a child's completion status to its parent without usage. The Hub therefore sums each conversation's own requests once into `insight.session_totals`; `insight.main_conversation_totals` excludes subagents. The [ordinal implementation](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/rollout/src/ordinal.rs) confirms that the replay boundary uses explicit persisted ordinals, not physical line numbers.

### Linking Harness processes to Sessions

The Hub links each stretch of a Session to the [Harness process](#harness-processes) that ran it, so a Session's requests can be set beside the CPU and memory its process tree used. A Session resumed in a new process links to both processes, each for its own stretch. `insight.request_links` computes the links each time it is read. The Hub stores each Session's stretches and refreshes them whenever anything they are computed from changes ([ADR-0016](decisions/0016-session-stretches-and-totals-are-stored-and-refreshed.md)), so `insight.session_stretches` can lag a change by one refresh, about 15 seconds. Either way a link lasts exactly as long as its Session and its process, and a rebuild or a delete changes it with nothing to redo. A link means that one process the Collector saw, and no other it saw, could have run the stretch. A process the Collector never saw can still have run part of a linked stretch, as **Processes the Collector did not see** below describes.

**Clocks.** Every time the link compares comes from the observed System's own clock: a request's time, which the Harness writes; a process's start, end, readings, and last sighting, which the Collector reads; and a Vitals sample's time. The Hub's clock stamps only when a Report arrived, which the link never reads, so a Hub whose clock is off, even by many seconds, links the same. What is left is the precision of a process's start. It is to the second, from the boot time and the kernel's start ticks on Linux and from the kernel or `etime` on macOS, so it reads up to two seconds early or one second late. A process's window therefore opens 2 seconds before its start. A seen end needs no allowance: it is the time of the tick that found the process gone, never before the process ended. A wall-clock step on the System while a process runs moves the transcript's times but not the process's start, so a step of more than 2 seconds can leave a stretch unlinked, or link it to a process it did not run when the step moves it into that process's window alone. The link relies on the System keeping time, as through NTP.

**Windows.** A process's window opens 2 seconds before its start. It **surely ran** until its seen end. While the Hub holds it as running, it surely ran only until 60 seconds, four reading intervals, after its last sighting, since a System whose Reports stopped arriving says nothing of what ran after. After a missed end, it surely ran until its last sighting. It **may have run** until its seen end, and while the Hub holds it as running, without end. After a missed end, it may have run until the Collector looked again: the Hub bounds that by the end of the first 5-minute Vitals bucket after the one that holds the last sighting, since the Collector that sent those Vitals was reading the process table and no longer saw the process. With no Vitals since, it may still be running. Vitals rollups are pruned after a year; a missed end older than that may then have run until a later bucket, which can only unlink a stretch, never link one.

**Candidates.** The candidates for a Session at a time are the processes of its System and Harness that may have run then, from 2 seconds before the start, and whose working directory is the Session's first or last one or is unknown. A process's working directory is the last one the Collector read, and the Hub keeps no earlier one, so the rule assumes a Harness process keeps the directory it started in. A process that changed directory is compared by its new one: it can drop out of a Session it ran in its old directory and leave another process there as the only candidate.

**Stretches.** A stretch of a Session is the Session's requests, its subagents' included, within one longest span of time over which its candidates stay the same, from the first of those requests to the last. Every request belongs to exactly one stretch. A window that opens or closes between two requests starts a new stretch, even if the candidates on either side are the same processes. A Session with no requests has no stretches. A stretch is:

- `linked` to a process when that process is its only candidate, the process's working directory is the Session's first or last one, the process surely ran until the stretch's last request, and the Collector read the process during the stretch: a reading of it lies between the stretch's first and last request. Its last sighting counts as a reading. Readings are kept for 14 days; after that, a whole 5-minute rollup of its readings within the stretch counts as one, so a shorter stretch can lose its link when its readings are pruned, and never gains one.
- `ambiguous` when two or more processes are its candidates: the Hub cannot tell which one ran it, and it links to none. Two processes of one Harness in one directory at once make every stretch they both may have run ambiguous, as does a Session that moved between two directories with a process in each, or a process in a directory the Collector could not read beside another candidate.
- `unmatched` otherwise: it has no candidate, or its one candidate is in a directory the Collector could not read, did not surely run until its last request, or was not read during it.

One process can run several Sessions in turn, as after `/clear`, or at once, as after `/resume` within it, and their stretches all link to it.

**Processes the Collector did not see.** A process the Collector never saw is no candidate: a Harness run as a script under another runtime, a process that started and ended between two readings, one that ran while the Collector was not running, and any beyond the 512 a section lists. That is why a link needs a reading of its process during the stretch. The Collector read the whole process table then, so a process that made requests of the stretch on both sides of that reading was running at it and was seen. A stretch an unseen process ran between two readings has no reading inside it and stays unmatched, and so does a stretch from before its process was first seen. What remains is a Harness the Collector cannot recognize or that a full section left out while it ran, and an unseen process that made requests of a stretch a seen process ran too, so the stretch links to the seen process, the unseen process's requests included. That happens when an unseen process resumes a Session between two readings after a seen process ran it, and when an unseen process starts a Session between two readings and a seen process resumes it later. No rule can tell these apart, since the Collector never read the unseen process. A seen end stamped before a stretch's last request, which a clock step can cause, leaves that stretch unmatched.

### The insight views

The views carry facts and locators, never transcript content, and read no chunk of a transcript. A locator is a System, a source, a path within the source, a generation, and a byte offset in the generation's uncompressed content, from which a reader on the Hub's System can find a line. Times are `timestamptz`, token counts `bigint`, and dollar amounts and context fill `numeric`. A Vitals sample's `cpu_busy_percent` and `load_1` and a process's `cpu_cores` are `double precision`, as the Collector measures them. A request's counts are bounded, so no total can overflow a `bigint`. Every view but the totals carries `parser_version`, the version that wrote its rows. A Session a delete is deriving again is in none of them. `insight.session_totals`, `insight.session_model_totals`, and `insight.session_stretches` read what the Hub stored at its last refresh, which `serve` runs every 15 seconds, so they can lag a change, a new Session included, by that long, and after a parser switch until the refresh has reached every Session of its Harness ([ADR-0016](decisions/0016-session-stretches-and-totals-are-stored-and-refreshed.md)). Changing a view's columns is a documented change ([ADR-0014](decisions/0014-session-insight-is-a-rebuildable-projection-read-through-insight-views.md)).

Every view in this table but `insight.parse_status` starts with the Session's key: `harness`, `system`, `source`, and `session_id`, the Harness's id for the Session.

A day-long overlay of Sessions on Vitals reads `insight.session_stretches` for the day instead and sets each stretch beside the samples from its `started_at` to its `ended_at`.

### Cost

Cost is list-price cost (glossary): what a request's tokens would cost at the model's API list prices on the day they were used, an approximation and not what a subscription plan billed. `insight.requests` computes it when read. `insight.session_totals` reads the totals the Hub stores, computed by the same rules, and a price change marks every Session's totals for the next refresh ([ADR-0016](decisions/0016-session-stretches-and-totals-are-stored-and-refreshed.md)). A price fix therefore shows within a few refreshes, with no rebuild.

**The price table** has one entry per model, `valid_from` day (UTC), and prompt tier, with a price in US dollars per million tokens for each kind of token: `input`, `output`, `cache_read`, `cache_write_5m`, and `cache_write_1h`; and the model's `context_window` in tokens, which Claude Code transcripts do not record. An entry may also carry `promptOver`, a prompt size in tokens, for a model that reprices the whole request above it; see below. The Hub bundles real list prices for the Anthropic models Claude Code runs and the OpenAI models Codex runs (`packages/hub/src/prices.ts`, which records each provider's source and when it was read), and `serve` loads them into the database when it starts.

**Which entry applies.** A request is priced by the entry for its model with the latest `valid_from` on or before the request's time, so a change of price is a new entry and never reprices an earlier request. A model id is matched without a trailing `-YYYYMMDD`, so `claude-haiku-4-5-20251001` takes `claude-haiku-4-5`'s entry. A request before its model's first entry, or for a model with no entry, is unpriced. The model name `unknown` is reserved for usage a Harness cannot attribute to a model, as Codex stores usage it cannot attribute to a turn, so a request for it is always unpriced: the price table refuses an entry for `unknown`, bundled or configured, and a configured one stops `serve` like any other entry that does not fit.

**Prompt tiers.** Some models reprice the whole request, every kind of token and not only the excess, when its prompt is over a size: Claude Haiku 5.5 over 100,000 tokens, and gpt-5.4, gpt-5.5, gpt-5.6 and gpt-6.x over 272,000. A tier is an entry with `promptOver`; an entry without it applies to every prompt. A request's prompt is its input, cache read, and cache write tokens together, which is `context_tokens`, so a prompt of exactly `promptOver` tokens is in the lower tier and one token more is in the higher. Of the entries in force at the request's time, the one with the highest `promptOver` the prompt exceeds applies, and among those the latest `valid_from`. Tiers are independent: a dated entry replaces only its own tier, and a model that stops tiering needs a new entry for each tier it had. A model with a tier has a base entry from the same date, or its smaller prompts are unpriced.

**Configuration overrides.** `[prices] overrides` in the Hub's configuration file, `--price-overrides`, or `HEIMDALL_PRICE_OVERRIDES` names a JSON file, `{"prices": [...]}`, whose entries have the table's fields: `model`, `validFrom` (`YYYY-MM-DD`), `input`, `output`, `contextWindow`, and optionally `cacheRead`, `cacheWrite5m`, `cacheWrite1h`, and `promptOver`. A relative path resolves from the working directory the Hub runs in. A file that cannot be read or does not fit stops `serve` before it touches the database, with a line that names the file. Overrides are dated like the bundled entries and follow the same rule, so a dated override never reprices an earlier request. Where a configured entry and a bundled one have the same model, `valid_from`, and prompt tier, the configured entry wins; otherwise the entry with the latest `valid_from` applies in its tier, whichever it came from. An entry omits a cache price the model has none of, and a request with tokens of that kind is unpriced.

**What each token kind costs.**

- Input, output, and cache read tokens cost their own price. Reasoning tokens are within output tokens and cost the output price once.
- A cache write costs `cache_write_5m` at the 5-minute TTL and `cache_write_1h` at the 1-hour TTL. A write the Harness did not split into the two costs the 5-minute price, the TTL Claude Code writes by default, and a 1-hour count above the write total leaves no negative 5-minute remainder. Anthropic prices them at 1.25 and 2 times input. OpenAI states one write price, for gpt-5.6 and later, and no TTL; it is the `cache_write_5m` price, as for an unsplit write, and a 1-hour write on such a model is unpriced.
- A cached input token, which OpenAI prices apart from input and Codex reports within its input count, costs `cache_read`. Cost reads `input_tokens` as excluding cached input, as Claude Code's counts do, so a Harness whose input count includes cached input, as Codex's does, stores the uncached part in `input_tokens` and the cached part in `cache_read_tokens`; otherwise a token would be priced twice, and `context_tokens` would count it twice.

**The columns.**

- `insight.requests` ends with `cost_usd`, `context_window`, `context_fill_percent`, and the cost by kind of token. `cost_usd` is null, never 0, when no entry applies to the request, and when the applying entry has no price for a kind of token the request used, such as a cache write on a model with no write price. `context_window` is the applying entry's window in tokens, null only when no entry applies and the Harness recorded none, so a request can have a window and no cost. A window the Harness recorded on the request, as Codex does, takes precedence over the entry's, so a request whose model has no entry can still have a window. `context_fill_percent` is `context_tokens` as a percentage of `context_window`, null when `context_window` is.
- `input_cost_usd`, `output_cost_usd`, `cache_read_cost_usd`, and `cache_write_cost_usd` split `cost_usd` by kind of token. A cache write is the 5-minute write plus the 1-hour write. Each is null when no entry applies to the request, and when the entry has no price for the kind of token it covers and the request used it. When `cost_usd` is not null none is, and the four sum to it.
- `insight.session_totals` and `insight.main_conversation_totals` end with `cost_usd`, `priced_cost_usd`, and `unpriced_requests`. `unpriced_requests` counts the Session's unpriced requests. `cost_usd` is the sum of the requests' costs, and is null when any request is unpriced, so a partial sum is never read as the total; a Session with no requests costs 0. `priced_cost_usd` is the sum over the priced requests alone, a lower bound when some are not, and null when none is priced.

## Purging a retired System

`heimdall-hub purge system <system>` deletes everything the Hub holds for a System that is no longer paired:

- its row, with its Last seen and Collector details
- its Vitals samples and rollups, and its disk rollups
- its Conditions, with their Timeline, their deliveries, and its stored limits. `serve` stores the limits again when it starts, if `hub.toml` still names the System.
- its load and hot-process evaluations
- its mirrored records, runs, checks, and Service stops
- its Harness installs and Harness processes
- its update and reboot observations, and its transcript spool status

The purge runs in one transaction, so a purge that fails deletes nothing. It refuses a System that is paired or that holds a pending Pairing code, and `heimdall-hub unpair` clears both. It exits 1 when the Hub holds nothing for the name, so a mistyped name purges nothing. Once purged, the System leaves the dashboard, its unpaired view included, and the records read.

The System's transcripts stay, with the [Session insight](#session-insight) derived from them, so its Sessions and their cost still count. When the Hub next refreshes the stored stretches, none links to a purged Harness process. `--transcripts` deletes the transcripts and their Session insight too. Unlike `heimdall-hub transcripts delete`, it deletes each generation's row, so the Hub keeps no record of their paths. After a purge that kept them, `purge system --transcripts` deletes them; without `--transcripts`, it exits 1 and says to add it. A System paired again under a purged name starts with no history, and the transcripts kept under that name are its own again. Like `serve`, the command first applies any pending database migrations.

## Purging a forgotten Service

`heimdall-hub purge service <system> <service>` deletes the Service stops and the [Service down](#service-down) and [Service restarted](#service-stops) Conditions the Hub holds for a Service on one System, with their Timeline and their deliveries, so the Service leaves the System's history, the Timeline, and its Condition pages. It works whether the System is paired or not, and leaves every other Condition alone, including one of another kind whose subject has the same name.

The provisioner forgets the Service first, with `heimdall-collector forget service <service>` on the System. A stop under way when the Service is forgotten ends at the Collector's next Service check and is sent in its next Report, so the purge follows that Report. A purge before that Report is followed by that stop and a new Service restarted note, which purging again removes. The purge refuses while the Hub's copy of the System's records still holds a `service` record of that name, and exits 1. An unreadable `service` record does not hold it back, although it holds back clearing Service down. Open Service down and Service restarted Conditions are deleted too, and no recovered message follows. The purge runs in one transaction, in order with the System's Reports, and waits out an [alert delivery](#alert-delivery) pass in progress, as a silence does. Stops alone or a Service restarted note alone count as something held. It exits 1 when the Hub holds nothing for the Service on that System, so a mistyped name purges nothing. Like `serve`, the command first applies any pending database migrations.

## Trust

Collectors send Reports with their System's token, but the dashboard, its records read included, has no authentication; it relies on a tailnet only its operator can reach. Its database holds every transcript, including anything an agent read. Authentication, and handling of secrets in transcripts, come before Heimdall is used anywhere else.

The Hub's database has two readers. The Hub's own role reads everything, transcripts included, and [ADR-0009](decisions/0009-collectors-pair-with-the-hub.md) treats that access as trusted. The insight reader is narrower: a role the provisioner creates and names in the Hub's configuration, which reads the [`insight` views](#the-insight-views) and nothing else ([ADR-0014](decisions/0014-session-insight-is-a-rebuildable-projection-read-through-insight-views.md)). It cannot read the tables beneath them, so no transcript, token, or Pairing code, and Vitals and Harness processes only as the views show them, and it cannot write to any table or view. Each view is a security barrier, so the reader's own filters run only on the rows a view shows: no error or function a filter raises can show a row a view hides, such as a Session a delete is deriving again or a deleted generation's path. A view a migration creates or replaces says `WITH (security_barrier = true)` each time, since CREATE OR REPLACE VIEW resets it, and a test fails for any `insight` view without it. A view calls only functions that read no table: a security-invoker function that reads a table beneath the views would deny the reader. The views carry facts and locators, not transcript content. A few columns are text as the Harness or the Collector wrote it rather than an id: the working directories, repository, and branches in `insight.sessions`, a Harness process's working directory and repository in `insight.harness_processes` and `insight.vitals_processes`, and the paths of transcript files. Raw transcript lines reach a reader only through [`heimdall-hub transcripts show`](#upload-protocol), on the Hub's System. [Querying the insight views](insight-reader.md) describes the role, its configuration, and example queries.

Within the database, the insight reader keeps what PostgreSQL lets every role do, less what the Hub's role can take away. When the Hub's role owns its database, `serve` revokes the right to create temporary tables from every role but the owner. The insight reader needs PostgreSQL 15 or later, where no role but the database's owner can create objects in the `public` schema by default. What only a superuser can change remains: any role can call PostgreSQL's large object functions, such as `lo_create`, which store data that persists, unless the provisioner revokes them; any role can take advisory locks, including the one the Hub's migrations take, which holds a starting Hub back while it is held; and any role can run queries as long and as heavy as the server allows. [ADR-0009](decisions/0009-collectors-pair-with-the-hub.md) treats database access as trusted, and the insight reader is trusted the same way not to abuse those rights; it is never trusted with what the views leave out.
